# 단계별 개발 계획

단계 M0~M6은 모듈 ID MOD-01~12와 다른 식별자다. 기간은 고정하지 않고 동작·검증 게이트로 진행한다. PDF100개/248쪽은 수령했다. 첫 구현은 교육·대화 계약부터 진행하고 PDF 게시/권한/검색은 M3에서 검증한다.

| 단계 | 구현 범위 | 완료 게이트 |
|---|---|---|
| M0 계약·환경 | 모듈 경계 검토, Python/DB/SDK 선택, Compose·마이그레이션·clock·가짜 모델 | 모듈/DTO 합의, 테스트 DB와 개발 DB 분리 |
| M1 교육 도구 | MOD-04/07/03과 MOD-02 최소 실행, 두 도구·상한·메모리 observer | 실제 모델→도구→답변, T-05/06/09~12/19의 교육 범위 |
| M2 대화 | MOD-02/01 영속 조립, 메시지 receipt·복구·후속/모호성 | 격리·멱등 재전송·동시성·실패·늦은 완료, T-01~03/05~08의 교육 범위 |
| M3 권한·원문 RAG | MOD-09/05/06/11의A, 로컬 세션, 수령 PDF 파일럿→100개 | T-04/07/08/10의 문서 범위, T-13~18/22/23/34 |
| M4 Wiki와 비교 | MOD-10/11의B, 빌드·검수·갱신·동일 조건 실험 | strict/fallback·권한 교집합·원문 연결, T-24~29/35 |
| M5 IT 지원 | MOD-12, 조회·준비·확인·멱등성·감사 | 확인 전 무생성·동시/유실/철회, T-30~33 |
| M6 UI·최종 검증 | MOD-08 실제 연결, PC·모바일, 전체150문항·보고서·Docker | T-20/21 및 전체 적용 테스트, 재현 데모 |

UI의 읽기 전용 연결은 M2/M3부터 작게 진행해도 된다. 진행 상황 스트리밍(D-29)은 실행 단계 기록이 생기는 M2 이후에 서버 쪽부터 붙이고, 화면 표시는 UI를 연결할 때 함께 한다. 답변 본문을 검사 전에 보내지 않는다. M4와 M5를 모두 끝내기 전에 화면을 완전히 꾸미는 작업을 우선하지 않는다. 각 단계에서 테스트를 추가한다. T-21은 실제 확인 UI가 연결되는 M6 게이트이며, M5의 서버 수정/확인/만료·멱등성은 T-30~33으로 검증한다.

M0부터 CurrentActor 포트·기본 거부 경계와 변경 요청 Origin 검사를 둔다. M1~M2의 서버 고정 test_stub은 [첫 구간](12-first-milestone-spec.md) 규칙대로 사용한다. M3에서 같은 포트에 실제 세션과 CSRF를 연결한다. stub 단계 결과를 최종 인증 통과로 보고하지 않는다.

## 공부와 구현 연결

1. SDK Tool Calling: 제안과 서버 실행을 분리해 M1 완성.
2. 상태·async·DB 원자성: M2 대화/예산/실패 처리.
3. 세션·RBAC/ACL·PDF 추출·Embedding·pgvector: M3 원문 근거와 권한.
4. 사전 지식 정리·출처 검수·평가: M4 Wiki와 A/B.
5. 멱등성·동시성·안전한 쓰기: M5 티켓 확인.
6. HTTP 상태·접근성·관측·배포 재현: M6.

LangGraph·MCP·별도 검색 엔진·클라우드는 필요한 이유와 측정 결과가 생기면 후속 검토한다.

## 수령 PDF의 게시 전 인계

목록·manifest·조직/규칙 일관성부터 확인하고 오류 보고서를 만든다. 미제공 시행일/ACL을 임의 채우지 않는다. 평가 gold는 PDF 검수 후 만든다. 초기15~20개 파일럿은 부분 성과로 표시하고 최종100개 완료와 혼동하지 않는다.

## 현재 상태

설계 개정과 통합 업무지원 정적 UI 시안이 있다. 사용자 PDF100개는 수령했고 수령 목록·대표 원문을 확인했다. backend는 M2까지 구현했다(2026-10-17, `backend/`).

- M0: Compose DB(PostgreSQL 18+pgvector)·개발/테스트 DB 분리·Alembic·clock·test_stub actor·닫힌 오류 사전·Origin 검사·health·가짜 모델.
- M1: MOD-04 교육 조회·HTTP, MOD-07 Anthropic 어댑터, MOD-03 교육 도구 2개, MOD-02 실행 반복·상한·근거 원장(메모리 observer), 개발용 CLI. 가짜 모델 테스트와 실제 모델 smoke 6개(프롬프트 m1-training-2)가 통과했다.
- M2: MOD-01 대화·메시지·run HTTP, 원자 수락과 같은 키 재전송, 조건부 완료와 늦은 완료 무시, 시작·조회·수락 시 만료 회수, 영속 observer, receipt로 검증한 교육 사본을 모델 문맥에 제공(프롬프트 m2-training-1). 가짜 모델 테스트는 통과했고, 실제 모델 확인은 별도 승인 후 진행한다.

- 진행 상황 스트리밍(D-29, 2026-10-17): 같은 메시지 POST에 `Accept: text/event-stream`. 기록된 단계만 progress로, 최종 결과는 검사·commit 뒤 result 하나로 보낸다. 연결이 끊겨도 실행은 계속된다. 화면 표시는 UI 연결 때 한다.

- M3(2026-10-18, 구현): MOD-09 로컬 세션·CSRF·인가(데모 조직 D-30), MOD-06 PDF 파싱·청크·임베딩 준비, manifest 초안·T-18 검증, MOD-05 게시·권한 두 겹 검색·근거/PDF, MOD-11 raw 검색(날짜·판본 필터·되묻기), MOD-03 search_documents, MOD-02 근거 원장·예산·인용, MOD-01 인용 저장·문서 권한 가림. 파싱은 100개 전체를 검사했다([파싱 보고](corpus/04-pilot-parse-report.md)).
  - **남은 것(사용자 결정 필요):** 개발 DB 게시는 manifest 검수(available_from 결정, [P-15](15-policy-options.md#p-15)) 전이라 하지 않았다. 100개 전체 임베딩은 Gemini 무료 티어 일일 한도(1,000건) 때문에 최소 이틀이 걸린다(2026-10-18 464/1,545 캐시). 시험 DB에서만 시험 전용 값으로 게시해 검증했다. 실제 모델이 도구 없이 빈 답을 내는 문제는 [P-16](15-policy-options.md#p-16) 결정 대기다.
  - 실제 모델 smoke(시험 DB, 8개 PDF, 프롬프트 `m3-docs-5`): 문서 6개 중 4개, 교육 8개 중 7개 통과(실패는 빈 답 2건·교육 ID 오기 1건, 서버가 거절).
  - 날짜 검증 보강 뒤(2026-10-18, `m3-docs-7`): 문서 6개 중 5개, 교육 8개 모두 통과. 실패 1건(D3 날짜 없는 질문)은 모델이 도구 없이 빈 답을 낸 [TS-24](portfolio/troubleshooting.md#ts-24)와 같은 경우이며 서버가 MODEL_OUTPUT_INVALID로 거절했다([P-16](15-policy-options.md#p-16)). 비용은 공시 가격 × 토큰으로 약 $0.016(콘솔 청구와 대조 안 함).
  - 사건 날짜 근원 검증(사용자 문장 대조·시제로 연도 추론)은 명세대로 구현했다([P-17](15-policy-options.md#p-17)). 시제·역할 표지는 O-13 임시 목록이다([P-05 보충](15-policy-options.md#p-05-o13)). 소수 시나리오 확인이며 평가 결과가 아니다.
  - T-17(2026-10-18): 안내 판본 선택(IT-045/046), 원규정 공백 시 결론 보류(`normative_gap`, 사건 단위), 우선관계 없는 충돌은 양쪽 인용(프롬프트 `m3-docs-8`)을 구현했다. 반대편 판본 경과조항 확장과 문서 우선관계(authority_relations)는 D-40으로 이어서 구현했다. 실제 모델 smoke(`m3-docs-8`): 문서 6/6, 교육 8/8.
  - 남은 결정 반영(2026-10-18, D-36~D-40): manifest 검수본(`review-manifest`, 공개 시각=시행일 00:00 KST), 빈 첫 답 1회 재호출, 부분 되묻기 문구, 시제 목록 확정, 문서 우선관계 표시(48건)·경과조항 확장(2건)·other_events. 그래서 위 T-17의 경과조항·우선관계 부분도 구현됐다.
  - 실제 모델 smoke(`m3-docs-9`, 2026-10-18): 교육 8/8, 문서 4/6. 실패 2건은 도구 없는 빈 첫 답으로, D-37 재호출이 동작했지만 두 번째도 빈 답이라 회복하지 못했다(0/2). 같은 날 `m3-docs-8`에서는 6/6이었다. 표본이 작아 원인은 판단하지 않는다.
  - 남은 것: 100개 전체 임베딩(1,545개 중 464개 캐시, Gemini 무료 티어 일일 1,000건이라 이틀 더 필요) → 그 뒤 개발 DB 게시와 실제 문서 smoke.
  - 알려진 한계(M3에서 구현하지 않음): 모델 입력 `knowledge_date`는 아직 받지 않는다(보내면 TOOL_ARGUMENT_INVALID). 되묻기를 받은 사건을 모델이 current 기준으로 다시 검색하는 것은 서버가 기억해 막지 않는다(사건 기준 규범은 current 검색에서 걸러짐). 이력 메시지의 연도 생략 날짜는 그 메시지를 보낸 날이 아니라 이번 실행 시각으로 추론한다(대부분 90일 제한에 걸림). 여러 사건 중 일부만 되묻기일 때는 D-39로 서버 되묻기 문구를 붙인다.

Wiki(M4), 티켓(M5), 실제 UI 연결과 평가150문항(M6)은 미구현이다. 실제 모델 smoke 통과는 소수 시나리오 확인이며 평가 결과가 아니다. 정적 시안의 검증과 각 단계 서버 테스트 통과를 구분한다. 체크박스나 성능 숫자를 실제 실행 전에 완료로 표시하지 않는다.

T-34는 M3 실행/수집/원문 검색 주입 방어와 M4 Wiki 빌드/검색 주입 방어 부분으로 나눠 게이트를 적용한다. MOD-10은 M4 범위이며 M3에 위키 구현을 요구하지 않는다.
