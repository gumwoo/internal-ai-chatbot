## TS-01 모델이 조회 없이 "확인 중입니다"를 최종 답으로 냄

- **증상:** 실제 모델 smoke 6개 중 "12월 25일에 열리는 교육 있어?"(0건 시나리오)만 실패했다(5/6 통과). 결과는 `MODEL_OUTPUT_INVALID`였다. 이 실행에는 모델 호출 1회만 있었고 도구 호출은 없었다.
- **재현:** 원인을 모르는 채 프롬프트를 고치지 않았다. 대신 무효 출력의 이유를 내부 note와 로그에 남기도록 고친 뒤, 같은 시나리오만 3회 다시 실행했다.

  | 회차 | 도구 호출 | 모델이 낸 최종 답 | 서버 판정 |
  |---|---|---|---|
  | 1 | 없음 | answer 빈 문자열 | 실패(`answer:string_too_short`) |
  | 2 | 없음 | answer 빈 문자열 | 실패(`answer:string_too_short`) |
  | 3 | 없음 | "확인 중입니다.", outcome=answered | **형식상 통과**(테스트의 outcome 검사에서만 걸림) |

- **원인:**
  - 확인한 사실: 3회 모두 첫 응답에서 도구 없이 최종 JSON을 냈다.
  - **추정(검증 안 함):** 문구로 보아 모델은 조회하려 했으나, 최종 JSON 형식(`output_config`)이 강제된 상태에서 도구 호출 대신 자리표시 답을 낸 것으로 보인다. 날짜 범위(custom)를 직접 계산해야 하는 질문이었다는 차이가 있지만 원인인지는 확인하지 않았다.
- **해결:**
  1. 프롬프트를 `m1-training-2`로 고쳤다. "조회를 마치기 전에는 최종 답을 내지 않는다", "중간 안내·빈 문장을 최종 답으로 쓰지 않는다", 특정 하루의 날짜 범위 규칙을 넣었다. 시험 문항("12월 25일")은 예시에 넣지 않았다.
  2. 이후 [M1 독립 검증](#ts-04)에서 지적을 받아 서버도 막게 했다. `no_results`는 이번 실행에 성공한 목록 조회가 있을 때만 인정한다.
- **검증:**
  - 0건 시나리오 3/3 통과(매회 `list_trainings` 1회 후 `no_results`), 전체 smoke 6/6 통과.
  - 대가: 프롬프트가 길어져 1회 호출 입력이 2,242 → 2,523~2,611 토큰으로 늘었다.
  - 비용(실제 토큰 × 공시 가격, Console 청구액과 대조하지 않음):

    | 실행 | 입력/출력 토큰 | 금액(USD) |
    |---|---|---|
    | 첫 smoke 6개 | 21,584 / 1,132 | 0.002724 |
    | 진단 재실행 3회 | 6,726 / 116 | 0.000730 |
    | 수정 후 0건 3회 + 전체 6개 | 42,630 / 1,989 | 0.005258 |

- **배운 점:** 형식 검증(JSON 스키마)을 통과한다고 정답이 아니다. "확인 중입니다"는 스키마상 완벽한 답이었다. 원인을 기록할 수단부터 만든 뒤 고쳐야 같은 비용으로 재현과 수정을 함께 확인할 수 있다.

## TS-02 테스트가 날짜 경계·시간 상한 결함을 잡지 못함

- **증상:** M1 테스트는 168개가 모두 통과했다. 그런데 독립 검증 에이전트가 코드를 일부러 망가뜨리는 mutation 14종을 넣어 보니 9종이 테스트를 그대로 통과했다(**검증 에이전트 실행**). 예: KST 00시 경계를 UTC로 바꿈, 종료 비교 `<`를 `<=`로 바꿈, 모델 20초 상한 제거, 기본 시도 수 6→7.
- **재현:** 날짜 경계 데이터가 경계 정각에 없었다. 테스트의 "오늘 09시 교육"이 하필 UTC 00시와 같아서 UTC 경계로 바꿔도 결과가 같았다.
- **원인:** 코드와 테스트를 같은 작성자가 써서 같은 맹점을 공유했다. 가짜 모델에 처음부터 정답을 넣어 두고 그 값을 다시 확인하는 테스트도 있었다(항상 통과).
- **해결:**
  - 경계 정각 데이터를 추가했다: 10/19 00:00, 10/26 00:00, UTC로는 전날인 10/16 08:30 KST, 영문 제목, 같은 시각 두 건, live_clock 종료 정각.
  - 상한 기본값 테스트와, 남은 시간이 상한보다 길 때 상한에서 끊기는 테스트를 추가했다.
  - 가짜 모델이 문제 값을 직접 내는 테스트로 바꿨다.
- **검증:**
  - 저장소 밖 mutation 플러그인으로 날짜·정렬·live_clock 결함 6종을 넣었고, 6종 모두 새 테스트가 실패로 잡았다.
  - 수정 전 커밋(`a9217ea`)을 임시 worktree로 꺼내 새 테스트를 돌렸다. DB가 필요 없는 테스트 28개, DB 테스트 9개, manifest 테스트 1개가 실패했다(결함을 실제로 잡는다는 뜻).
  - 이 과정에서 테스트 자체의 결함도 2건 나왔다.
    - manifest 테스트가 테스트 DB에 남은 이전 실행 행을 읽고 통과하고 있었다. 테이블을 비우게 고쳤다.
    - 새 테스트가 제 수정 코드의 중복 ID 버그를 잡았다. 사본이 20건이어야 하는데 19건이 됐다.
- **배운 점:** "테스트 통과"는 테스트가 결함을 잡는다는 증거가 아니다. 예전 코드에서 새 테스트가 실패하는지, 결함을 넣으면 실패하는지를 함께 본다.

## TS-03 테스트 DB 보호를 URL 쿼리로 우회 가능

- **증상:** 테스트는 DB 이름이 `_test`로 끝나고 개발 DB와 다를 때만 돌게 막아 두었다. 그런데 검증 에이전트가 이 검사를 우회하는 URL을 찾았다.
- **재현:** `postgresql+psycopg://…/agent_test?dbname=agent_dev`에서 검사 함수는 `agent_test`를 돌려주는데, SQLAlchemy psycopg dialect가 만드는 실제 접속 인자는 `dbname=agent_dev`였다(직접 재현). 이 URL이면 테스트의 `TRUNCATE`와 `downgrade base`가 개발 DB에서 실행된다.
- **원인:** 이름 검사가 URL의 경로만 봤다. dialect는 URL 쿼리를 접속 인자에 덮어쓴다.
- **해결:**
  - `make_url`로 해석하고, 접속 대상을 바꾸는 쿼리 키(`dbname`, `database`, `host`, `hostaddr`, `port`, `service`, 대소문자 무관)가 있으면 거절한다.
  - 같은 커밋에서 `APP_ENV`·`AUTH_MODE` 기본값도 없앴다. 설정이 빠졌을 때 test_stub 인증으로 조용히 켜지지 않는다.
- **검증:** 우회 URL 5종을 거절하는지 테스트한다. 이 테스트들은 수정 전 커밋에서 실패한다([TS-02](#ts-02)의 방법). API 이미지를 설정 없이 띄우면 `app_env`·`auth_mode` 누락으로 시작을 거절하는 것도 확인했다.

## TS-04 되묻기·0건 답에서 서버가 모델 출력을 그대로 믿음

- **증상:** 검증 에이전트가 세 가지를 지적했다. 모두 가짜 모델로 직접 재현했다.
  - "어느 교육인지" 되묻는 답에 모델이 선택값을 넣으면 그대로 저장됐다(인수 기준 "임의 선택 저장 금지" 위반).
  - 조회가 인자 오류로만 끝났거나 조회를 아예 하지 않았는데 `no_results`(0건)가 정상 완료됐다.
  - 대화 사본이 20건을 넘으면, 방금 다시 조회한 교육이 사본에서 밀려났다.
- **원인:** 최종 답 검증이 "원장에 있는 ID인가"만 봤다. outcome과 실제 조회 기록의 관계는 보지 않았다.
- **해결:**
  - 되묻기·0건이면 선택값을 서버가 비운다.
  - `no_results`는 이번 실행에 성공한 목록 조회가 있을 때만 인정하고, 교육 ID가 붙어 있으면 무효로 본다.
  - 사본은 옛 사본 → 이번 결과 → 답이 가리킨 교육 순으로 쌓아 뒤에서 자른다.
  - 검증 에이전트는 "0건일 때만 허용"을 제안했지만, 목록 7건을 받고 해당 교육이 없다고 답하는 경우도 정상이라 "성공한 조회가 있을 때"로 정했다.
- **검증:** 해당 테스트 5개는 수정 전 커밋에서 실패하고 수정 후 통과한다.

<a id="ts-05"></a>
## TS-05 `localhost` 접속이 응답 없이 멈춤

- **증상:** 개발 DB(Docker, `127.0.0.1:5440`)에 Alembic 마이그레이션을 실행하자 120초 안에 끝나지 않았다.
- **재현:** 같은 DB에 psycopg로 직접 접속(`connect_timeout=5`)해 비교했다. `127.0.0.1`은 0.02초, `localhost`는 5.03초(제한 시간 만료 후 다음 주소로 넘어감)였다.
- **원인:** 이 PC에서 `localhost`가 IPv6(`::1`)를 먼저 시도했다. Docker 포트는 IPv4 loopback에만 열려 있었다. **추정:** `::1` 시도가 거절되지 않고 응답 없이 기다린 것으로 보이지만, 그 원인(Docker Desktop 등)은 확인하지 않았다.
- **해결:** `.env.example`과 문서의 DB 호스트를 `127.0.0.1`로 바꾸고 이유를 주석으로 남겼다.
- **검증:** 같은 명령의 마이그레이션 왕복이 정상 종료했다.

<a id="ts-06"></a>
## TS-06 DB가 꺼지면 health/ready가 130초 동안 응답 없음

- **증상:** "DB가 없을 때 503" 테스트 하나가 130.02초 걸렸다. 전체 60개 실행 시간은 135.45초였다.
- **원인:** 접속 시간 제한이 없어 OS의 TCP 재시도를 그대로 기다렸다. 서비스로 치면 ready 엔드포인트가 2분 넘게 응답하지 않는 결함이다.
- **해결:** 엔진에 `connect_timeout`(기본 5초, libpq 최소 2초)을 두고, ready 검사 전체에 `asyncio.timeout`을 걸었다.
- **검증:** 같은 테스트 2.01초, 전체 60개 4.50초. 테스트에 "10초 안에 503" 조건을 넣었다.

<a id="ts-07"></a>
## TS-07 Windows에서 uvicorn 루프 지정이 실패

- **증상:** `--loop agent.shared.db:selector_loop_factory`로 띄우자 `TypeError: BaseSelectorEventLoop.close() missing 1 required positional argument: 'self'`가 났다.
- **원인:** psycopg async는 Windows 기본 Proactor 루프를 지원하지 않아 Selector 루프가 필요했다. 설치된 uvicorn 0.54 소스(`config.py get_loop_factory`)를 읽어 보니, 사용자 지정 문자열은 "루프 팩토리를 돌려주는 함수"가 아니라 **팩토리 그 자체**로 쓰였다. 제 함수가 클래스를 돌려주자 그 클래스가 인스턴스처럼 다뤄졌다.
- **해결:** `--loop asyncio:SelectorEventLoop`를 직접 넘기고 래퍼 함수를 지웠다.
- **검증:** 로컬 uvicorn과 Docker 컨테이너 모두에서 health·ready 200, Origin 없는 POST 403을 확인했다.

<a id="ts-08"></a>
## TS-08 실제 `.env`로 바꾸자 서버가 시작하지 않음

- **증상:** 그때까지는 명령에 환경 변수를 직접 넣어 실행했다. 사용자가 `.env.example`을 복사한 `.env`만으로 실행하자 설정 검증이 `embedding_dim: Input should be 768 or 1536 [input_value='1536']`으로 실패했다.
- **원인:**
  - `Literal[768, 1536]` 필드가 환경 변수 문자열 `"1536"`을 숫자로 바꾸지 않았다.
  - 같은 점검에서 `ANTHROPIC_API_KEY=`처럼 빈 값이 "미설정"이 아니라 빈 문자열로 들어오는 것도 발견했다.
- **해결:** `int`로 받은 뒤 허용값을 검사하고, `env_ignore_empty=True`를 켰다.
- **검증:** `.env.example`을 그대로 복사한 파일로 설정이 만들어지는지 보는 테스트를 추가했다.
- **배운 점:** 테스트 환경과 실제 환경의 입력 경로(환경 변수 문자열)가 다르면 같은 코드도 다르게 동작한다. 설정 예시 파일 자체를 테스트 입력으로 쓴다.

<a id="ts-09"></a>
## TS-09 코드 주석이 모델에 보내는 도구 스키마로 샘

- **증상:** 실제 호출 전에 dry-run으로 요청 본문을 열어 보니, 도구 스키마의 `description`에 Pydantic 모델 docstring("HTTP 쿼리와 list_trainings 도구 인자가 같은 모델을 쓴다…")이 들어 있었다.
- **원인:** `model_json_schema()`가 클래스 docstring을 스키마 설명으로 넣는다.
- **해결:** 도구 명세를 만들 때 인자 모델의 최상위 `description`을 빼고, 도구 설명은 별도 필드로 둔다.
- **검증:** 모델에 보내는 스키마에 `description`과 서버 전용 필드(`user_id`·`field_origins` 등)가 없는지 테스트한다.
- **배운 점:** 모델에 실제로 나가는 요청을 사람이 직접 보는 단계(dry-run 기본값)가 이런 문제를 비용 없이 잡는다.

<a id="ts-10"></a>
## TS-10 실제 모델 호출 뒤 "Event loop is closed"

- **증상:** 첫 smoke 실행 로그에 `RuntimeError: Event loop is closed`가 났다(httpcore2 연결 종료 중).
- **원인:** 테스트마다 만든 `AsyncAnthropic` 클라이언트를 닫지 않아, 이벤트 루프가 끝난 뒤 가비지 수집이 연결을 닫으려 했다.
- **해결:** 어댑터에 `aclose()`를 두고 CLI·테스트·앱 종료 시 닫는다.
- **검증:** 수정 후 smoke 6개 실행 로그에서 해당 오류 0건. 닫기 호출을 확인하는 단위 테스트를 추가했다.

<a id="ts-11"></a>
## TS-11 시작 시 회수가 서버 시작을 막아 테스트가 약 7배 느려짐

- **증상:** M2에서 "앱 시작 시 만료 run 회수"를 넣자 전체 테스트 시간이 102.45초(237개)가 됐다. 직전 전체 실행은 14.28초(233개)였다.
- **원인:** lifespan에서 회수를 기다렸다. DB 없이 도는 HTTP 테스트들이 앱을 띄울 때마다 접속 제한 시간만큼 멈췄다. 실제 서버라면 DB가 늦게 뜰 때 서버 시작이 같은 이유로 늦어진다.
- **해결:** 시작 회수를 백그라운드 작업으로 돌리고, 종료 시 정리한다. 회수에 실패해도 조회·수락 진입에서 다시 회수된다(실행 계약).
- **검증:** 같은 237개 14.04초. 시작 회수가 실제로 만료 run을 닫는지 테스트한다.

<a id="ts-12"></a>
## TS-12 응답 시각이 KST/UTC로 섞이고 목록 상태가 항상 비어 있음

- **증상:** 가짜 모델 테스트는 모두 통과한 상태에서, 실제 uvicorn에 요청을 보내 확인하다가 두 가지를 발견했다.
  - 대화 생성 응답의 `created_at`은 `+09:00`인데, 같은 대화 조회는 `2026-10-17T11:24:31…+00:00`이었다.
  - 대화 목록의 `active_run_id`가 실행 중에도 항상 `null`이었다.
- **원인:**
  - DB에서 읽은 시각(세션 시간대 UTC)을 KST로 바꾸지 않았다.
  - 목록 응답에 값을 하드코딩해 두었다.
- **해결:** 응답 시각을 모두 KST로 통일하고, 목록에 실제 값을 낸다.
- **검증:** 생성·조회·이력·run의 모든 시각이 `+09:00`인지와, 실행 중 목록에 활성 run이 보이는지 테스트한다.
- **덤:** 같은 확인에서 대화 생성이 처음엔 실패했다. 서버 결함이 아니라 Windows Git Bash의 curl이 한글 본문을 cp949로 보낸 탓이었다. httpx로 UTF-8을 보내 다시 확인했다.

<a id="ts-13"></a>
## TS-13 같은 테스트 DB를 쓰는 테스트 실행이 간헐 실패

- **증상:** 검증 에이전트가 전체 테스트를 6회 돌려 1회 실패했다(**검증 에이전트 실행**). 오늘 교육 목록에서 한 건이 빠졌다.
- **원인(추정):** 같은 시각에 다른 검증 에이전트도 같은 `agent_test`에서 테스트를 돌리고 있었다. 한쪽의 `TRUNCATE`·`downgrade base`가 다른 쪽 데이터를 지웠을 가능성이 크다. 원인은 확인하지 못했다.
- **해결:** 테스트 DB를 쓰는 세션 동안 PostgreSQL advisory lock을 잡아 프로세스 사이를 직렬화한다.
- **검증:** 이후 검증 에이전트 2개를 동시에 돌리는 조건에서 실행했다(결과는 [M2 독립 검증](#m2-review)에 기록).

<a id="ts-14"></a>
## TS-14 보호 훅이 `.env`를 언급만 해도 명령을 막음

- **증상:** AI 코딩 도구(Claude Code)의 보호 훅이 `.env` 파일 접근을 막도록 되어 있었다. 그런데 grep 패턴이나 커밋 메시지에 `.env`라는 글자만 있어도 명령이 차단됐다.
- **원인:** 명령 문자열에 `.env`가 들어 있으면 차단하는 단순 판정이었다.
- **해결:** 파일 인자로 쓰이거나, 따옴표·heredoc 안에서 파일 접근 동사와 붙은 경우만 차단하도록 좁혔다. 따옴표 짝이 맞지 않으면 넓게 막는다(fail-closed).
- **검증:** 45개 사례 테스트를 저장소 밖 임시 폴더에서 실행했다.
- **배운 점:** 가드레일은 너무 넓으면 우회하고 싶어지고, 너무 좁으면 쓸모가 없다. 실제 오탐 사례를 테스트로 남긴다.

<a id="m2-review"></a>
## M2 독립 검증 결과

M2(대화 저장·멱등 재전송·만료 회수) 구현 뒤 검증 에이전트 2개를 동시에 돌렸다. 하나는 실행 생명주기를, 하나는 통합·보안·테스트를 맡았다. 두 에이전트가 같은 테스트 DB를 썼지만 [TS-13](#ts-13)의 advisory lock 덕분에 간섭 실패는 보고되지 않았다. 결과는 P1 1건(조건부), P2 다수였고, 아래 4건으로 묶어 고쳤다. 같은 묶음에서 실패·만료 응답에 `run_id`가 빠진 문제(04-api-spec 위반)도 고쳤다.

<a id="ts-15"></a>
## TS-15 최종 저장 실패 시 답변 본문이 로그에 남음

- **증상:** 두 검증 에이전트가 각각 독립적으로 찾았다. 한쪽은 P1(조건부), 다른 쪽은 P2로 분류했다.
- **재현:** 가짜 모델이 NUL 문자(`\x00`)가 섞인 답을 내게 해서 메시지 저장을 실패시켰다. 응답은 503 `PERSISTENCE_FAILED`로 올바르게 나갔지만, 로그에 SQL 파라미터째 답변 본문이 남았다(검증 에이전트 실행, 저장소 밖 탐침으로 직접 재현).
- **원인:** DB 엔진에 `hide_parameters`를 설정하지 않았다. 실패 처리에서 `logger.exception`이 SQLAlchemy 예외 문자열(파라미터 포함)을 그대로 남긴다.
- **위반한 기준:** [T-03](../07-test-and-evaluation.md) "비밀/제한 본문·원문 자유문장의 일반 로그 유출 없음"(M2 게이트).
- **해결:**
  - DB 엔진에 `hide_parameters=True`를 둬서 모든 SQL 오류 메시지에서 파라미터를 뺀다.
  - MOD-01의 실패 로그는 traceback 대신 예외 종류와 run_id만 남긴다. 일부 DB 오류는 메시지 자체에 값이 실릴 수 있어서다.
  - 모델 답의 NUL은 저장 전에 지운다. 사용자 입력의 NUL은 저장 실패(재시도 가능 503)가 아니라 입력 오류(422)로 거절한다.
- **검증:**
  - NUL 섞인 답은 200으로 저장되고(NUL 제거) 로그에 본문이 없다.
  - DB 트리거로 실제 INSERT를 실패시키면 503 `PERSISTENCE_FAILED`와 `run_id`가 나가고, 로그에 본문이 없다.
  - `hide_parameters=False`로 되돌리는 mutation을 테스트가 잡는다.

<a id="ts-16"></a>
## TS-16 수락과 만료 회수의 잠금 순서가 반대라 교착

- **증상:** 메시지 수락은 대화 행을 먼저 잠그고 run을 갱신한다. 완료·실패·만료 회수는 run을 먼저 갱신하고 대화 행을 나중에 갱신한다(코드 순서는 직접 확인).
- **재현:** 검증 에이전트가 GET run의 회수를 첫 UPDATE 뒤 멈춘 사이에 같은 대화로 POST를 보냈다. 수락 쪽이 `DeadlockDetected`로 끝나 503이 났다(검증 에이전트 실행). 데이터 손상은 없고 요청 하나가 실패한다.
- **원인:** 같은 두 행을 서로 다른 순서로 잠근다. 재시작 직후 백그라운드 회수가 도는 동안 첫 메시지가 들어오거나, 202 뒤 GET run을 polling하며 새 메시지를 보내면 일어날 수 있다.
- **해결:** 모든 쓰기 경로(수락·완료·실패·만료 회수)가 "대화 행 → run" 순서로 잠근다. 여러 대화를 한 번에 회수할 때는 대화 ID 순서로 잠근다. 같은 김에 수락·완료 시각을 잠금을 얻은 **뒤에** 잡게 했다. 그래야 잠금 대기 시간만큼 영속 deadline과 단조 시계 deadline이 어긋나지 않는다.
- **검증:**
  - 교착 테스트 2개: 회수와 수락이 겹치는 경우, deadline 뒤 실패를 저장하는 중에 회수가 겹치는 경우. 둘 다 통과한다.
  - 처음 쓴 교착 테스트는 첫 SQL 직후에 멈췄는데, 그 SQL은 잠금을 잡지 않는 SELECT였다. 그래서 잠금을 빼는 mutation을 잡지 못했다.
  - "잠금을 잡는 첫 SQL(UPDATE·FOR UPDATE) 직후 멈춤"으로 바꾸자, 완료·회수 경로의 대화 잠금을 지우는 mutation 2종을 모두 잡았다.
- **배운 점:** 동시성 테스트는 "멈추는 지점"이 맞아야 의미가 있다. 잠금을 쥐기 전에 멈추면 교착이 날 수 없는 상황을 만들 뿐이다.

<a id="ts-17"></a>
## TS-17 권한 없는 사용자의 모델 문맥에 교육 사본이 들어감

- **증상:** `training.read`가 없는 사용자로 후속 질문을 보냈다. 이력에서는 이전 답변이 가려졌지만(모델 이력 roles `user, user`), system 프롬프트의 "대화 자료"에는 `TR-SEC-001`과 장소가 그대로 들어갔다. 모델이 교육 ID 없이 장소를 말하면 200 `answered`로 가려지지 않고 나간다(검증 에이전트 실행, 직접 재현).
- **원인:** 사본은 receipt로만 검증하고 현재 권한은 다시 보지 않았다. 가림 판정은 답의 `training_refs`만 봤다. 모델 문맥에 들어간 의존 자원을 모은 `dependency_ids`는 저장만 하고 쓰지 않았다.
- **위반한 기준:** CT-03 "이력을 모델이나 UI에 보내기 전 현재 권한을 재검증", "모델이 인용을 생략해도 접근 검사를 피하지 못한다". 교육 fixture는 로그인 사용자에게 공개라 지금 피해는 작다. 하지만 같은 구조가 M3 문서 권한으로 이어지므로 지금 막는다.
- **해결:**
  - 모델 문맥에 넣는 사본도 현재 권한으로 거른다.
  - 답변 가림은 답에 적힌 참조(`training_refs`)가 아니라, 모델 문맥에 들어간 의존 자원 전체(`dependency_ids`)로 판정한다.
- **검증:**
  - 권한 없는 사용자의 모델 문맥에 사본이 없다("대화 자료: 없음").
  - 가린 답이 이력·모델 문맥·재전송 응답 모두에서 빠진다.
  - 모델이 교육 ID를 생략하고 사본으로 답한 경우도 가린다.
  - 해당 mutation(권한 필터 제거, refs 기준 가림)을 테스트가 잡는다.

## TS-18 M2 테스트가 생명주기·가림 규칙을 검증하지 못함

- **증상:** M2 테스트는 258개 모두 통과했다. 그런데 검증 에이전트의 mutation에서 다음 결과가 나왔다(검증 에이전트 실행).
  - 생명주기 쪽: 9종 모두 생존. 예: 실패한 run이 활성 소유권을 풀지 않음, `asyncio.shield` 제거, `FOR UPDATE` 제거, deadline 경계 `>`→`>=`.
  - 통합 쪽: 24종 중 15종 생존. 예: 가린 답변을 모델 이력에 포함, 다른 대화의 receipt를 사본 검증에 사용, 이력 창을 "가장 오래된 12개"로 바꿈.
- **원인:** [TS-02](#ts-02)와 같은 구조다. 정상 흐름은 촘촘하게 확인했지만, "하면 안 되는 것"을 일부러 일으키는 테스트가 부족했다. 예를 들어 사본 검증 테스트는 receipt가 처음부터 하나도 없는 대화만 봤다. 가림 테스트는 원래 답변에 없던 문자열의 부재를 확인해 항상 통과했다.
- **해결:** 생존 mutation마다 그 결함을 실제로 일으키는 테스트를 하나씩 추가했다(`tests/test_conversation_review.py` 22개). 예시는 다음과 같다.
  - 실패 뒤 다음 메시지 수락
  - 요청 취소·서버 종료 뒤에도 실행 완료
  - 같은 키 동시 요청이 200·202·202
  - deadline 정각 도착, deadline 뒤 실패
  - 다른 대화·실패 run의 receipt 불신
  - 이력 창이 최근 12개
  - HTTP 경계값과 헤더
- **검증:**
  - mutation 32종을 저장소 밖 사본에서 다시 돌렸다. 검증 에이전트에서 생존했던 24종과, 이번 수정을 되돌리는 8종이다.
  - 1차는 26종을 잡았다. 테스트 3개를 다시 고친 뒤 최종 31종을 잡고 1종이 생존했다.
  - 남은 1종(수락의 명시적 `FOR UPDATE` 제거)은 같은 트랜잭션의 만료 회수가 대화 행을 다시 잠가 동작이 같아지는 경우다(동등 mutation).
  - 전체 테스트는 280개 통과(실제 모델 smoke 8개는 기본 제외).

검증 결과 중 판단이 갈리는 것은 사례가 아니라 선택지로 남겼다: CP-07 위치([P-12](../15-policy-options.md)), 대화 자료를 넣는 위치([P-13](../15-policy-options.md)), 공백만 있는 입력([P-14](../15-policy-options.md)).

  - 확인한 사실: P2는 항상 재현된다. 모델은 되묻기 판단(`needs_clarification`)은 맞게 하지만 되묻는 질문을 `answer`에 쓰지 않는다. 사본이 있는 되묻기 smoke("두 교육 중 그 교육")는 질문 문장을 채웠다.
  - **추정(검증 안 함):** 프롬프트가 `answer`를 "사용자에게 보여 줄 한국어 답변"이라고만 설명해서, 모델이 "되묻기에는 답이 없다"고 해석한 것으로 보인다.
  - P1의 지난 실패(지금까지 7회 중 1회)는 간헐적이다. 그 실행의 원래 응답은 기록하지 않아 원인을 모른다.
- **해결(두 겹):**
  1. 프롬프트 `m2-training-2`: "되묻는 경우에도 answer에는 사용자에게 할 질문을 한국어 문장으로 쓴다", "어떤 outcome이든 비워 두지 않는다"를 넣었다. 대상을 대화 자료에서 찾을 수 없을 때도 되묻도록 규칙 5를 넓혔다.
  2. 서버 보완: `needs_clarification`인데 answer가 비면 서버의 일반 질문 문구로 채운다. 결과에 `answer_source=server_fallback`을 남겨 모델이 쓴 답과 구분한다. 다른 outcome의 빈 답은 서버가 대신 쓸 수 없어서 그대로 실패시킨다.
  3. 실제 모델 smoke가 호출마다 원래 응답(stop_reason·내용 블록)을 기록하게 했다. 간헐 실패를 다시 돌리지 않고 확인하기 위해서다.
- **검증:**

    - 새 대화 되묻기는 이번에도 모델이 빈 답을 냈고, 서버 보완으로 통과했다.
    - 후속 질문("그중 보안교육 장소는?")은 도구를 다시 부르지 않고, 검증된 대화 자료만으로 "3층 교육장"이라고 답했다. 실제 모델로 [ADR-08](adr.md#adr-08)이 동작함을 처음 확인했다.

- **배운 점:** 같은 증상(빈 답)이라도 원인이 다를 수 있다. [TS-01](#ts-01)은 "조회 전에 최종 답을 냄", 이번 P2는 "되묻기에서 질문을 비움"이었다. 원래 응답을 기록해야 구분된다.

## TS-20 종료 저장 중 예상 밖 예외에서 SSE가 결과 없이 끊김

- **증상(검증 에이전트 실행, 직접 재현):** 진행 상황 스트리밍 구현 직후 독립 검증에서 찾았다. 종료 저장(`_complete`) 안에서 `RuntimeError` 같은 예상 밖 예외가 나면 다음과 같았다.
  - SSE는 progress 3개만 보내고 `result`·`error` 없이 끝났다. 명세의 "종료 이벤트는 정확히 하나"를 어긴다.
  - JSON 경로는 503 `SERVICE_UNAVAILABLE`이었지만 `run_id`가 없었다. 수락 뒤 오류에는 run_id를 붙인다는 규칙도 어긴다.
- **원인:** 종료 저장 함수가 DB·OS 오류만 잡았다. 그 밖의 예외는 실행 task의 예외로 남았고, SSE 쪽은 `task.result()`에서 그 예외를 받아 스트림 자체가 깨졌다.
- **해결:** 종료 저장에서 모든 `Exception`을 "저장 실패"로 다룬다(`CancelledError`는 `BaseException`이라 제외). 두 경로 모두 run_id가 붙은 `PERSISTENCE_FAILED` 하나로 끝나고, run은 deadline 뒤 회수된다.
- **같이 찾은 테스트 공백(검증 에이전트 실행):**
  - 실제 ASGI 연결 끊김 경로를 테스트하지 않았다. 기존 테스트는 제너레이터를 `aclose()`했다. 실제 서버는 `asyncio.wait` 대기 중에 취소를 보낸다. "취소되면 실행도 취소" mutation이 살아남았다. ASGI 2.3 `http.disconnect`를 보내는 테스트를 추가했다.
  - heartbeat 뒤 남은 대기(getter)를 취소하지 않으면 다음 단계를 가로채 사라진다. 이 mutation도 살아남았다. 단위 테스트를 추가했다.
  - "실행 task를 기다리지 않음" mutation은 종료를 heartbeat 주기(15초)만큼 늦춘다. 기존 테스트는 결국 통과했다. 시간 상한(5초)을 단언했다.
  - `Accept: text/event-stream;q=0`(거부)도 SSE로 응답했다. q=0을 제외했다.
- **검증:** SSE mutation 17종(내가 만든 13종 + 검증 에이전트가 찾은 생존 3종 + 이번 수정 되돌리기 1종)이 모두 잡혔다. 전체 테스트 통과.
- **배운 점:** "정확히 하나"처럼 개수를 약속하는 계약은 정상·알려진 실패만이 아니라 예상 밖 예외에서도 지켜야 한다. 테스트 대체 경로(`aclose`)와 실제 경로(ASGI 취소)가 다르면 대체 경로의 통과는 실제를 보장하지 않는다.
- **같은 기간 관찰(원인 미확인, 수정하지 않음):** 실제 서버 확인 중 "다음 주 보안교육 장소 알려줘"가 도구 호출 없이 빈 답(`answer:string_too_short`)으로 실패했다(1회). [TS-19](#ts-19)에 적은 미해결 현상과 같은 모양이다. 연결을 끊은 실행이었지만 run은 끝까지 진행돼 failed로 저장됐다. 끊김과는 무관하다. 실제 호출 2회 비용은 입력 8,859 / 출력 277 토큰, $0.001024(공시 가격 기준, Console 청구액과 대조 안 함)다.

## TS-21 세션 회수 뒤에도 권한 판정이 허용, 웹 세션에 운영 권한(MOD-09)

- **증상(검증 에이전트 실행, 직접 재현):** MOD-09 구현 뒤 독립 검증에서 나왔다. 기존 테스트 61개는 모두 통과한 상태였다.
  - 로그아웃한 세션에서 만든 actor 사본으로 `authorize`를 부르면 허용됐다. 명세는 "세션 회수·현재 auth_revision 확인"을 요구한다.
  - 직원 계정에 operator 역할이 붙으면 웹 세션 actor가 `ops.*`를 그대로 가졌다. 지금은 그런 HTTP 경로가 없지만, 앞으로 capability만 보는 운영 경로가 생기면 직원 세션이 운영자로 승격된다.
  - 비밀번호 해시(scrypt, 1회 약 65ms)를 이벤트 루프에서 계산했다. 잘못된 비밀번호 동시 20회로 루프가 최대 486ms 멈췄다(검증 에이전트 측정).
- **원인:** ActorContext에 "어느 세션에서 나왔는지"가 없어 사용자 행만 다시 읽었다. capability를 역할에서만 계산하고 actor 출처(source)별 제한을 두지 않았다.
- **해결:**
  - local_session actor에 서버 내부 값 `session_ref`(세션 토큰 hash)를 두고, Authorize가 그 세션의 회수·만료를 확인한다(CT-01 갱신).
  - 웹 세션 actor에서 ops.*·eval.*를 뺀다. 운영 actor는 서버 설정의 운영 계정으로만 만들고 ops.*만 갖는다.
  - 비밀번호 검증을 스레드로 옮기고 동시 4개로 제한했다.
  - 같이 고친 P3: ASCII가 아닌 CSRF 헤더가 503이 되던 문제(bytes 비교로 403), 로그인 NUL 입력 503(422), 정책 audience 타입 오류, 재적재가 비활성 계정을 되살림, 비밀번호 변경 시 기존 세션 유지, 재적재 역할 변경 감사 없음, 없는 역할로 멤버십 변경 시 처리 안 된 DB 오류.
- **검증:** MOD-09 변이 37종(내가 만든 26종 + 검증 에이전트 생존 10종 대응 + 이번 수정 되돌리기)이 모두 잡혔다(대상 문자열이 바뀐 2종은 코드에서 없어져 제외). 동시 로그인 8회 중 루프 최대 정지가 60ms 미만인지 테스트로 확인한다.
- **배운 점:** "요청 시작 때 확인했다"와 "판정 시점에 다시 확인한다"는 다르다. 권한 판정 함수에 무엇을 다시 읽는지(세션·역할·revision)를 계약에 적어 두어야 테스트가 그것을 겨눌 수 있다.

<a id="ts-22"></a>
## TS-22 변이 시험 16종이 "모두 잡힘"으로 나왔지만 실제로는 실행 실패였음

- **증상:** M3 검색 경로에 변이 16종을 넣었더니 전부 "잡힘"으로 나왔다. 그런데 결과 줄이 모두 `1 error in 7초` 안팎으로 똑같았다. 실패(failed)가 아니라 수집 오류(error)였다.
- **원인:** 변이 실행기가 소스를 임시 폴더로 복사해 돌렸다. 설정의 저장소 루트(`REPO_ROOT`)를 소스 파일 위치에서 4단계 위로 계산하는데, 사본에서는 그 위치에 `docs/`가 없어 시험 fixture가 수령 목록을 읽지 못했다. 변이와 무관하게 모든 실행이 같은 이유로 깨졌다.
- **해결:** 사본을 `backend/` 바로 아래(원본과 같은 깊이)에 만들게 바꿨다. 사본 경로는 git 제외에 넣었다.
- **검증:** 같은 변이 2종을 다시 돌려 `1 failed, 10 passed`처럼 실제 시험 실패로 잡히는 것을 확인했다. 전체 19종을 다시 돌리자 13종 잡힘·6종 생존이 나왔다. 처음 결과(16/16)는 틀렸다.
- **배운 점:** "모두 통과" 못지않게 "모두 실패"도 의심해야 한다. 실패의 종류(failed/error)와 소요 시간이 모두 같으면 시험 대상이 아니라 시험 장치가 깨진 것이다. [ADR-12](adr.md#adr-12)의 "검증 도구 자체도 검증한다"가 다시 필요했다.

<a id="ts-23"></a>
## TS-23 재게시가 과거 corpus snapshot의 결과와 권한을 바꿈(P1)

- **증상(검증 에이전트 실행, 직접 재현):** 같은 파일을 다른 메타데이터로 다시 게시하면, 이미 게시한 v1 snapshot에서도 결과가 바뀌었다. 9/20 사건 검색이 종전 ED-031이 아니라 현행 ED-030을 돌려줬다. 문서 키를 바꾸면 그 문서가 다른 키의 ACL로 묶여 노출이나 차단이 생겼다.
- **원인:** 판본 행을 snapshot과 공유하면서 재게시 때 그 행을 그 자리에서 UPDATE했다. 주석에는 "판본 식별 값은 바꾸지 않는다"고 적었지만 코드는 식별 값까지 덮어썼다.
- **해결:** 게시된 판본은 불변으로 했다. 재게시에서 저장된 메타데이터와 하나라도 다르면 바뀐 필드 이름과 함께 거절한다. manifest의 ACL이 저장된 정책과 다르면 조용히 무시하지 않고 거절한다(권한 변경은 감사가 남는 set_acl로만). 판본 메타데이터 수정 등록은 아직 지원하지 않는다고 MOD-05 메모에 남겼다.
- **같이 고친 것(검증 에이전트 실행):**
  - 안내 개정 쌍(IT-045/046)이 둘 다 검색됨 → 안내 개정 쌍에는 guidance_valid 구간을 필수로 하고 겹침·역전을 거절. 초안에 IT-046의 "적용 기간" 표기를 검수 메모로 남김.
  - 파싱 품질 문제(빈 페이지·cid·숫자 누락·span 오류)가 게시를 막지 않음 → 게시 거절.
  - 종전 규정 8건의 부칙 "제1조(시행일) 이 규정은 …시행한다."가 경로로만 쓰여 인용 불가 → 제목 줄에 본문이 붙은 조문은 단위로.
  - 철회된 문서를 이력 재검증에서 볼 수 있다고 답함 → 판본이 모두 철회된 문서 키는 제외.
  - 등록된 파일명이 다른 PDF를 가리키면 그대로 제공 → 제공 직전 SHA-256 대조.
  - 숨긴 결과 때문에 순위 번호가 비어 개수가 새던 문제, 정책 값이 문자열이면 SQL이 오류를 내던 문제.
  - Gemini 어댑터가 httpx 연결·시간 초과 예외를 그대로 내보냄 → 시간 초과·공급자 장애로 정규화.
  - 임베딩 속도 조절: 묶음이 분당 한도보다 크면 한도 초과, 429 대기 횟수가 작업 전체에 누적, 깨진 캐시 줄로 이어 가기 실패, 같은 텍스트 중복 요청.
  - 무료 티어 한도를 먼저 쓰고 나서 메타데이터 검사로 거절 → 메타데이터 검사를 임베딩 앞으로.
  - `draft-manifest`가 검수한 manifest를 덮어씀 → 있으면 `--force` 요구.
- **검증:** M3 변이 2차 20종 중 19종이 잡혔고, 남은 1종(게시 쪽 규범 구간 겹침 검사)은 그 검사를 직접 겨누는 테스트를 넣어 잡았다. 판본 메타데이터 덮어쓰기 되돌리기 변이도 잡힌다.
- **배운 점:** "snapshot은 불변"이라는 계약은 snapshot 테이블만이 아니라 snapshot이 가리키는 모든 행에 적용돼야 한다. 공유 행을 갱신하는 코드가 있으면 불변성은 깨진다.

## TS-24 실제 모델이 문서 질문에서 검색 없이 빈 최종 답을 냄(원인 일부 확인, 정책 결정 대기)

- **증상:** M3 문서 smoke 6개(시험 DB, 시험 corpus 8개 PDF, 실제 Gemini 임베딩)를 처음 돌리자 6개 모두 실패했다. 원래 응답을 보니 5개는 첫 호출에서 search_documents를 부르지 않고 바로 최종 JSON을 냈다(4개는 `{"answer": ""}` 출력 약 45토큰, 1개는 "문서 조회를 하지 못했습니다"). 1개(D6)는 검색했지만 관련 없는 사건 기준 규정 때문에 되묻기로 갔다.
- **진단(코드 변경 전 측정, 각 줄은 실행 횟수):**

  | 프롬프트 | 검색한 비율 | 비고 |
  |---|---:|---|
  | m3-docs-1(첫 smoke) | 1/6 | |
  | m3-docs-2(규정 질문은 먼저 검색) | 1/6 + 진단 0/4 | 바뀌지 않음 |
  | 변형 B(질문 분류 규칙을 교육 규칙 앞에) | 2/4 | 외부교육 한도 2/2, IT 접수 0/2 |
  | 변형 C(B + IT 접수도 규정 질문 + 검색 예고 금지) | 3/5 | IT 접수 3/3, 외부교육·출장 0/2 |
  | 변형 D(분류 규칙을 system 맨 앞에) | 2/6 | |
  | C + 빈 대화 자료 표시 | 0/6 | |
  | m3-docs-3(C 채택) smoke | 3/6 | |
  | m3-docs-4 smoke | 4/6 | 외부교육 한도 2개만 실패 |

  - 검색을 한 경우에는 매번 맞는 원문을 인용했다: 9/29 시작 외부교육 → 종전 ED-031 "1,000,000원", 9/29 출발 출장 → 종전 GA-082, IT 접수 항목 → IT-037 "1.2 필수 입력".
  - **교육 smoke 회귀도 함께 발견:** m3-docs-3에서 교육 8개 중 3개가 같은 모양(도구 없이 빈 답)으로 실패했다(M2 때 7/8). M3가 교육 경로에서 바꾼 두 가지를 갈라 봤다(다음 주 교육, 각 3회): 현재 1/3, `citation_ids` 필드 제거 3/3, 대화 자료가 없을 때 "없음" 표시 복원 3/3. 문서 답에는 `citation_ids`가 필요해 "없음" 표시를 복원했다(m3-docs-4). 이후 교육 8/8.
- **원인:**
  - 확인한 것: 실패는 모두 "첫 호출에서 도구 없이 최소 JSON"이다. 도구 스키마는 정상이고(같은 질문이 다른 실행에서는 검색함) 서버 검색·인용 경로는 실제 모델로 동작한다. 교육 회귀는 P-13 B로 system에서 "대화 자료: 없음" 줄이 빠진 것과 관련이 있다(복원 시 3/3, 표본 작음).
  - **추정(검증 안 함):** thinking을 끈 상태에서 JSON 스키마로 최종 답을 강제하면, 모델이 도구를 고르기 전에 형식만 맞춘 빈 답으로 끝내는 경향이 있다. 프롬프트 문구로는 줄었다 늘었다 하며 없어지지 않았다.
- **해결:** 프롬프트를 m3-docs-4로 조정했다(질문 분류 규칙, 빈 대화 자료 표시). 기준 조회는 가장 가까운 판본 1개만 보게 했다(되묻기 과민 대응). 남은 실패를 서버가 보정하려면 명세의 "무효 출력은 실패"를 바꿔야 해서 [P-16](../15-policy-options.md#p-16)으로 결정을 요청했다.
- **비용:** 이 사례의 실제 호출 전체(smoke 4회 + 진단 5회 + 교육 smoke 2회)는 입력 507,407 / 출력 13,743 토큰, 약 $0.058이다(공시 가격 기준, Console 청구액과 대조 안 함).
- **배운 점:** 출력 계약(필수 필드)과 문맥 배치(자료 위치) 같은 "사소한" 변경도 모델의 도구 선택을 바꾼다. 교육 smoke를 다시 돌리지 않았다면 회귀를 못 봤다. 프롬프트를 바꾸면 기존 시나리오도 함께 돌려야 한다.

## TS-25 Agent 연결 계층: 이력 의존 미전파·결론 매핑 누락·예산 순서(검증 에이전트)

- **증상(검증 에이전트 실행, 프로브 재현):** 문서 검색을 Agent에 연결한 뒤 독립 검증에서 P2 6건이 나왔다(P1 없음). 기존 테스트 427개는 모두 통과한 상태였고, 변이 21종 중 문서 테스트가 잡은 것은 7종이었다.
  - 제한 문서를 인용한 답을 이력으로 다시 요약한 답은 의존 자원이 비어, 권한 철회 뒤에도 보였다.
  - 검색이 미지원(90일 초과)·되묻기만 돌려줬는데 모델이 근거 없이 금액을 답해도 answered로 저장됐다.
  - 예산을 넘는 대표 그룹을 건너뛰고 더 낮은 순위 그룹을 넣었다. 빠진 그룹 ID도 남지 않았다.
  - 임베딩 키 누락·무효 응답이 "근거 부족" 200으로 끝났다(T-08 위반).
  - 최종 응답이 요청 시작 때의 actor로 판정됐다(실행 중 역할 변경·세션 회수 미반영).
  - 모델이 넣은 사건 날짜를 사용자 문장과 대조하지 않는다 → 명세 기능 미구현, 정책 결정 요청(P-17).
  - P3: 같은 검색 반복 시 예산 이중 계산, 판본 기준 필터를 LIMIT 뒤에 적용, event_key 자유 문자열(인용 DTO로 그대로 나감), 사용자가 "[대화 자료]" 표시를 입력해 서버 블록처럼 보이게 할 수 있음, 근거 조회가 공개 시각을 확인하지 않음, 시각 표기 혼재.
- **해결:** 이력 의존 합집합 저장, 서버 결론 매핑(answer_source=server_mapping), 예산은 처음 넘는 그룹에서 멈추고 대표 그룹 누락은 기권, 같은 그룹 재사용, 임베딩·검색 준비 실패는 모두 TOOL_EXECUTION_FAILED, 응답 직전 ReloadActor, event_key 식별자 패턴, 사용자 입력 표시 문자열 무력화, 근거 조회에 공개 시각 조건, 판본 기준 필터를 자르기 전에.
- **같이 찾은 것:** 수정 중 MOD-03이 MOD-07 타입(ModelCallError)을 import해 모듈 경계 검사가 실패했다. 오류 코드 집합으로 판정하게 바꿨다.
- **검증:** 변이 17종(검증 에이전트 생존 7종 + 이번 수정 되돌리기 9종 + 미인용 문맥 문서 1종) 모두 잡힘. 전체 테스트 통과. 실제 모델 smoke(m3-docs-5): 문서 4/6(실패 2건은 [TS-24](#ts-24)와 같은 빈 답), 교육 7/8(실패 1건은 모델이 교육 UUID를 몇 자리 빠뜨려 적어 서버가 원장 대조로 거절한 것, 의도한 방어).
- **배운 점:** 권한 가림은 "이번 답이 무엇을 읽었는가"만이 아니라 "이번 답이 기댄 이전 답이 무엇을 읽었는가"까지 따라가야 한다.

## TS-26 사건 날짜 근원 검증: 인용 대조는 통과했지만 틀린 날짜를 조용히 씀(검증 에이전트)

- **맥락:** 모델이 search_documents에 낸 사건 날짜를 그대로 쓰던 것을, 사용자 문장 인용(date_quote)을 서버가 본인 메시지와 대조·정규화하도록 바꿨다(명세 이행, [P-17](../15-policy-options.md#p-17)). 첫 구현의 테스트는 모두 통과했다.
- **증상(검증 에이전트 프로브 재현):** "인용이 메시지에 있다"만 확인하고 그 안의 날짜를 믿어서, 틀린 날짜가 verified로 나가는 경우가 여럿 나왔다.
  - 숫자 일부 인용: "11월 1일" 안의 "1월 1일"이 통과(문자열 포함 검사만 함).
  - 시제를 메시지 전체에서 봄: 다른 문장의 "다녀온"으로 예정 사건을 과거로 추론.

  - 런타임: 같은 support_group을 다른 사건(event_key·날짜)에서도 같은 인용 ID로 재사용, 한 검색의 대표 그룹이 예산으로 빠져도 다른 검색을 인용하면 answered, 이력의 사용자 메시지는 서버 표시 문자열 무력화 없이 들어감.
- **재검증(2차, 같은 날):** 1차 수정 뒤 다른 검증 에이전트가 프로브 38건으로 다시 찾았다. P1 4종이 남아 있었다.

  - 그 밖에 예정 날짜의 90일 제한 없음, "그제서야"의 "그제", 없는 전체 날짜 + "오늘"이면 오늘로 대체, 5자리 연도, "1.5배"의 점에서 문장이 끊김, 모델이 보지 못한 오래된 이력에서도 인용을 찾음.

- **2차 원인:** 1차 수정은 검사 범위를 "인용"으로 잡았는데, 인용 범위는 모델이 정한다. 모델이 짧게 자르면 검사가 사라진다. 또 시제를 "문장"에서 찾아, 날짜가 어느 동사에 걸리는지 보지 않았다.

  - 남긴 것: 여러 사건 중 일부만 되묻기일 때의 처리는 정책 질문으로 올렸다([P-18](../15-policy-options.md#p-18)). knowledge_date 입력, current 재검색, 이력 날짜의 기준 시각은 알려진 한계로 [개발 계획](../08-development-plan.md)에 적었다.
- **검증:** 1차 수정 뒤 변이 22종 중 15종만 잡혀(가정·문장 범위·시제 섞임·이력 무력화·date_basis 전달·assistant 출처가 생존) 테스트를 보강했다. 2차 수정 뒤 변이 30종(날짜 검사 24 + 런타임 연결 6)을 돌려 27종이 잡혔고, 생존 3종(시제 범위·사건 동사 시제·소수점 문장 분리)에 테스트를 더해 30종 모두 잡힘. 2차 검증 에이전트의 프로브 38건을 다시 돌리면 verified는 정상 사례(이력 인용) 1건뿐이다. 전체 테스트 513개 통과. 실제 모델 smoke(m3-docs-7): 문서 5/6(D4 "9월 29일에 출발해서 10월 2일에 돌아온" 포함, 실패 1건은 [TS-24](#ts-24)의 빈 답), 교육 8/8.
- **배운 점:** 검사 범위를 공격자(여기서는 모델)가 정하는 값에 맞추면 검사가 사라진다. 근원 검증은 "어디서 왔나"와 "무엇을 뜻하나"를 따로 시험해야 한다. 날짜처럼 해석이 들어가는 값은 지원하지 않는 표현을 되묻기로 보내는 쪽이 안전한 기본값이다.

## TS-27 T-17 규범 공백: 공백 검사가 "가장 가까운 판본"에 걸려 FAQ로 금액이 나감(검증 에이전트)

- **맥락:** M3 게이트 T-17(공지·FAQ·규정 충돌/위임)은 테스트가 0개였다. 명세가 정한 범위는 안내 판본 선택(IT-045/046), 원규정 공백 시 결론 보류, 반대편 판본 경과조항이다. 앞의 둘을 구현하고, 경과조항과 문서 우선관계(authority_relations)는 manifest 값이 모두 빈 목록이라 정책 질문으로 남겼다([P-19](../15-policy-options.md#p-19)).
- **첫 구현:** 기존 "날짜 되묻기" 로직을 따라 LookupApplicableBasis의 1순위 판본이 규범이면 그 판본의 적용 구간에 사건 날짜가 들어가는지 봤다. 공백이면 결과에 `normative_gap`을 붙이고, 그 검색 호출의 안내를 인용한 answered를 서버가 insufficient_evidence로 바꿨다. 테스트는 통과했다.
- **증상(검증 에이전트 프로브 7개로 재현):** P1 4종.
  - 1순위가 FAQ면 공백 검사를 아예 하지 않았다. FAQ가 질문과 가장 가까운 경우가 가장 위험한데 그때 검사가 꺼졌다("2024년 11월 1일 출발 출장 일비" → FAQ 인용 "5만 원" answered).
  - 공백 표시가 검색 호출 단위라, 같은 사건을 다른 질의로 먼저 검색해 받은 citation ID(재사용)를 인용하면 우회됐다. 호출 순서에 따라 결과가 달랐다.
  - `training_ids`가 있으면 보류를 건너뛰었다.
  - 모델이 날짜 기준을 잘못 고르면(교육비 질문에 trip_start) 교육 규범이 기준 불일치로 빠지고 공백 표시도 없어 FAQ 금액이 나갔다.
  - P2: 관련 없는 일반 기준 규범(결재권한 기준)이 1순위면 거짓 공백으로 정상 답을 막음, insufficient_evidence로 내면서 FAQ 금액을 쓰는 문장은 그대로 나감.
- **원인:** "어떤 규범의 공백인가"를 검색 순위에 맡겼고, "누구의 결론을 보류하나"를 사건이 아닌 검색 호출에 묶었다.
- **해결:** 공백 대상은 판본 후보 전체에서 이 날짜 기준에 대응하는 가장 가까운 규범(per_claim 제외, 일반 기준 규범은 사건 질문의 대상 아님). 사건 질문에 그 기준의 규범이 없고 다른 사건 기준 규범만 있으면 basis_mismatch로 되묻기. 보류는 사건 문맥(event_key·date_basis·as_of_date) 단위로, 공백 사건을 그날 유효한 규범 없이 인용했거나 공백 사건 말고는 인용이 없으면 answered·insufficient_evidence 모두 서버 문구로. 교육 ID 예외 제거. 모델에 document_type을 보여 주고 프롬프트(m3-docs-8)에 "안내는 규정을 바꾸지 못함, 우선관계 없는 충돌은 양쪽 인용"을 넣었다.
- **검증:** 변이 15종(공백 판정·보류·사건 단위·유효 규범 예외·근거부족 문장·안내 판본 구간·공개 시각·프롬프트 규칙 등) 중 처음 12종이 잡혔고, 생존 3종(일반 기준 규범 대상 포함·document_type 미전달·공개 시각 무시)에 테스트를 더해 15종 모두 잡힘. T-17 테스트 11개, 전체 524개 통과. 실제 모델 smoke(m3-docs-8): 문서 6/6, 교육 8/8(공시 가격 × 토큰 약 $0.019). D3 빈 답은 이번에는 나오지 않았지만 [TS-24](#ts-24)를 고친 것은 아니다(P-16).
- **남긴 것:** needs_clarification 문장은 바꾸지 않는다(다른 사건을 묻는 정상 되묻기를 지우지 않게). 규정끼리의 충돌은 서버가 판정하지 않고 프롬프트 규칙에 맡긴다.
- **배운 점:** 안전 검사를 검색 순위 1등에 걸면, 순위를 바꾸는 입력(질의 표현, 다른 문서의 가까움)이 곧 우회로가 된다. 보류 단위는 사용자가 묻는 사건이어야 한다.

## TS-28 경과조항·부분 되묻기: 사건 구분 키가 느슨해 되묻기가 사라지고, 없는 날짜 하나가 검색 전체를 막음(검증 에이전트)

- **맥락:** 남은 결정을 추천안대로 반영했다(D-36~D-40). manifest 검수본(공개 시각=시행일 00:00 KST), 빈 첫 답 1회 재호출, 부분 되묻기 문구, 시제 목록 확정, 문서 우선관계 표시(원문 명시 문장 48건)·경과조항 확장(CM-092 제9조, IT-041 제13조)·search_documents의 other_events(같은 사건의 다른 날짜)를 구현했다. 테스트는 모두 통과했다.
- **증상(검증 에이전트 프로브로 재현):**
  - P1: 부분 되묻기(D-39)가 사건을 event_key만으로 구분해, 모델이 event_key를 비우거나(None끼리 같은 사건) 같은 key로 날짜 없는 current 검색을 한 번 더 하면 "날짜 확인됨"으로 보고 되묻기 문구를 빼고 금액 답을 그대로 냈다.
  - P2: 경과조항 조건에 상신일이 필요하면 검색 전체를 되묻기로 바꿔, 10/1 이후의 결재 질문은 주제와 무관하게 거의 모두 상신일을 다시 물었다.
  - P2: 같은 경과조항을 그룹마다 붙여 한 검색에 같은 조항이 20번(서로 다른 citation_id) 들어갔다(예산 낭비).
  - P2: other_events에 같은 사건 기준이 두 번 오면 마지막 값으로 덮어써 순서에 따라 결과가 달랐다.
  - P3: 인용 DTO에 경과조항 표시 없음, 우선관계 대상 제목 조회에 공개 시각 조건 없음, 관계 검사가 기본 판본과 다른 application_basis·자기 문서 참조를 통과, 기권 문구로 바뀌면 다른 사건의 되묻기 문구가 사라짐.
  - 문제없음으로 확인: 제한 문서(CM-093) 제목은 권한 없는 사용자에게 나오지 않음, 우선관계 48건의 종류 분류가 원문과 일치, 경계일(9/30 상신·10/1 승인) 처리.
- **원인:** "같은 사건"의 기준을 모델이 고르는 값(event_key) 하나에 맡겼다. 또 명세의 "사건 하나라도 미확인이면 되묻는다"를 검색 결과 전체에 적용해, 기본 판본으로 답할 수 있는 경우까지 막았다.
- **해결:** 사건은 (event_key, date_basis)로 구분한다. 경과조항에 빠진 사건 날짜는 검색을 막지 않고 기본 판본 결과를 둔 채 후속 되묻기 문구(transition_pending)로 답 끝에 붙인다(명세의 "되묻거나"). 같은 조항은 결과 전체에서 한 번만 붙이고, 같은 사건 기준에 다른 날짜가 오면 쓰지 않는다. 인용 DTO에 source_role, 제목 조회에 공개 시각 조건, 관계 검사 보강, 기권 문구에도 되묻기 보존.
- **검증:** 변이 27종(경과조항 조건·비교·기준·공개 시각·역할 표시·검증 연결, 우선관계 가시성·분류·검사, 빈 첫 답 재호출, 부분 되묻기 사건 구분·중복·기권 문구 보존 등) 중 처음 23종이 잡혔고, 생존 4종 중 3종(반대편 판본 공개 시각·기권 문구의 되묻기·제목 공개 시각)에 테스트를 더해 잡힘. 남은 1종(경과조항의 application_basis 비교 삭제)은 관계 검사(기본 판본과 같은 기준)와 기준 필터가 같은 경우를 막아 결과가 달라지지 않는 동등 변이로 보고 이중 방어로 둔다. 전체 테스트 545개 통과. 실제 모델 smoke(m3-docs-9): 교육 8/8, 문서 4/6. 실패 2건은 도구 없는 빈 첫 답이었고 D-37 재호출이 동작했지만 모델이 두 번 다 빈 답을 내 회복하지 못했다(이번 측정 0/2, 비용 약 $0.017).
- **배운 점:** 서버가 지켜야 하는 구분(어느 사건인가)은 모델이 생략할 수 있는 선택 인자 하나에 걸지 않는다. "묻는다"는 규칙도 무엇을 막는지까지 정해야 과잉 차단이 되지 않는다.

## TS-29 M5 IT 티켓: 같은 키 동시 수정이 409, 오류 순서, "안 급해요"가 긴급, 출처 하나 틀리면 초안 전체 거절

- **맥락:** MOD-12(준비 draft → 화면 수정 pending → 확인 → 티켓, 취소·만료)를 명세의 상태 표·head 직렬화·멱등·입력 출처 규칙대로 구현했다. 테스트 18개는 처음부터 통과했다.
- **증상(검증 에이전트 프로브 7개로 재현, P1 없음):**
  - 같은 Idempotency-Key로 수정 두 건이 동시에 오면 replay(200) 대신 하나가 ACTION_SUPERSEDED였다. replay 검사가 head 잠금 밖에만 있었다.
  - 오류 우선순위가 오류 계약과 달랐다. 채택되지 않은 draft 확인이 ACTION_NOT_PREPARED가 아니라 RUN_NOT_ELIGIBLE, 취소된 draft 확인도 RUN_NOT_ELIGIBLE(상태 오류가 root 자격보다 먼저여야 함).
  - 확인 replay·반복 확인이 현재 열람 권한을 보지 않고 티켓 전체를 돌려줬다.
  - 긴급 여부 정규화가 "안 급해요·당장은 아니에요·빨리 안 해도 돼요"를 true로 바꿨다. "밤 12시"가 정오, "10시간째"의 10이 10시, 미래 발생 시각 허용.
  - P3: 채택되지 않은 draft가 GET으로 보임, 만료 감사 중복, CP-07 창 크기가 정책 값과 따로 고정.
- **실제 모델에서 나온 것:** 모델이 대상 서비스 "VPN"의 출처로 "VPN이 안 돼요"(값을 포함한 더 긴 구간)를 냈다. 출처 하나가 틀리면 초안 전체를 거절하자 모델이 출처만 빼고 같은 값을 다시 보내 3회 연속 실패했다(insufficient_evidence). 티켓 0건 답은 "교육 목록을 조회했을 때만 0건 인정" 규칙에 걸려 502였다.
- **해결:** 잠금 안에서 replay를 한 번 더 확인. 검사 순서를 오류 계약대로(소유권 → version·입력 → 성공 replay → 상태(확정 결과 → superseded → 취소 → 만료 → draft 확인 불가) → root 자격). replay·반복 확인에 현재 열람 판정. 부정 표현을 먼저 보는 긴급 규칙과 시각 규칙 보강. 확인하지 못한 필드는 저장하지 않고 비운 뒤 rejected_fields로 알린다(D-43, "사용자 입력만 저장"은 그대로). 값이 인용 구간 안에 정확히 한 번 있으면 서버가 구간을 좁힌다. 티켓 목록 조회도 0건 근거로 인정.
- **검증:** 변이 29종 중 처음 17종(설정 오류 4) → 테스트 보강 뒤 28종 잡힘. 남은 1종(준비 run 자격 검사 하나 제거)은 진입·저장 직전 두 번 검사하는 구조라 결과가 같은 동등 변이. T-30~33 테스트 28개, 출처 단위 21개, 전체 605개 통과. 실제 모델 티켓 smoke 3/3(m5-tickets-2, 약 $0.0036): 사용자 문장 그대로의 초안, 바꿔 쓴 제목은 비우고 다시 물음, 말하지 않은 영향 범위·자산번호는 비움.
- **배운 점:** "검증 실패 = 전체 거절"은 안전해 보이지만 모델과 함께 쓰면 같은 실패를 반복하게 만든다. 틀린 값을 저장하지 않는 것과 요청 전체를 막는 것은 다른 일이다.

## TS-32 평가 채점: 인용 하나로 정답, 위치로 정한 judge ID, 표기마다 다른 숫자

- **맥락:** A/B 비교를 실행하기 전에 평가 실행기·규칙 채점·judge·평가 CLI를 만들었다. 시험 8개가 통과했다. 그런데 이 단계는 독립 검증·변이 시험 없이 커밋돼 있었다(사용자 질문 "Gemini 없이 할 수 있는 일은 다 했나?"로 다시 확인).
- **증상(독립 검증 에이전트, 재현 포함):**
  - P1: answered 정답 조건이 "인용 하나가 gold와 맞음"뿐이었다. 근거 2개 중 1개만 인용하고 금지 금액을 말한 답도 정답이었다. 실측으로 answered 125문항 중 53문항에 금지 숫자가 있고 91문항은 근거가 2개 이상이다. D-49 예산 동결이 이 정답률에 기댄다.
  - P1: judge 익명 ID를 판정 순서 위치로 만들어, 입력 순서를 바꾸거나 다른 split을 판정하면 이전 판정이 엉뚱한 문항에 붙었다.
  - P2: 한도 초과로 실패한 판정이 다시 판정되지 않음. 같은 조항 안의 hard negative를 정답 답변에서도 오답으로 셈. "2026.10.01."·"2026년 10월 1일"·"110만 원"·"1,100,000원"이 서로 맞지 않음. 결과에 예산이 없어 설정이 다른 실행이 한 집계로 합쳐짐. 한 문항 예외가 전체 실행을 멈춤. 패킹 전 후보·답 속 제한 문서 제목은 누출 검사 밖.
- **원인:** 채점을 "지표 계산"으로만 보고, 그 지표로 어떤 결정을 내리는지(예산 동결)에서 정답 정의를 거꾸로 정하지 않았다. judge 블라인딩은 "라벨 숨기기"만 보고, 같은 답을 다시 찾는 식별자의 성질을 보지 않았다.
- **해결(D-51):** answered 정답 = 근거 하나 이상 인용 + 두 자리 이상 숫자 사실 모두 + 금지 숫자·별도 그룹 hard negative·누출 없음, 근거 집합 전체 인용은 rule_complete로 따로. 숫자는 날짜를 월-일로, "N만 원"을 원 단위로 맞추고 조항 번호를 뺀다. 한 자리 수는 규칙으로 핵심 여부를 가릴 수 없어 judge에 맡긴다(처음엔 모든 숫자를 요구했다가 "1회 과정"의 1 때문에 맞는 답이 틀리는 것을 시험에서 확인). judge ID는 (seed, 문항, 설정, 판정 입력) hash, 실패 행은 다시 판정. 결과에 실행 설정을 남기고 설정별로 집계·쌍 비교·누락/중복 보고. holdout은 `eval-freeze`로 기록한 예산으로만. 문항 예외는 기록하고 계속, `--resume`으로 실패 문항만 다시.
- **검증:** 변이 24종(정답 조건 3, hard negative 그룹, 누출 3, 정렬 2, 숫자 정규화 2, 설정 라벨, 쌍 비교·완결성, judge ID·재판정·형식, 실행 중단·holdout 잠금·이어하기, 전체 문맥 기준선 3, 질의 캐시 키) 중 처음 22종 잡힘. 생존 2종(별도 그룹 hard negative를 금지 숫자 없이 인용, 기준선의 날짜 기준 필터)은 시험 사례가 다른 조건에 먼저 걸렸던 것이라 사례를 더해 24종 모두 잡힘. 전체 백엔드 시험 677개 통과.
- **함께 측정한 것:** 빈 첫 답 강제 재호출(D-41, `tool_choice=any`) 교육 smoke 2026-10-18 실측: 8/8 통과, 강제 재호출 1회(0건 질문에서 첫 답이 비었고, 강제한 도구 호출 뒤 no_results로 정상 종료), 공시가 기준 $0.0063(직접 실행 6개 기준). 표본이 작아 비율은 판단하지 않는다.
- **배운 점:** 정답 정의는 그 숫자로 내릴 결정에서 거꾸로 정한다. 익명화 ID는 "숨기기"와 함께 "같은 것을 다시 찾을 수 있는가"를 만족해야 이어하기·병합이 안전하다.

## TS-33 100개 게시 뒤 첫 실제 실행: 모든 직원 질문이 400, 날짜 있는 규정 질문에 빈 되묻기, Wiki page 3분의 1 미게시

- **맥락:** Gemini를 유료로 바꿔 남은 임베딩 79개를 채우고(요청 4회) 개발 DB에 100개를 게시한 뒤, 전체 문서 smoke·Wiki 빌드·dev A/B를 처음으로 실제 모델로 돌렸다.
- **증상(모두 실측):**
  - dev A 실행 50문항이 전부 502(MODEL_UPSTREAM_ERROR). Anthropic 응답 원문: strict 도구 스키마의 선택 인자가 26개로 한도 24 초과. 선택 인자를 null 허용 필수로 바꾸자 다음 한도에 걸렸다: union 인자 28개, 한도 16. 원래 스키마도 union 22개로 이미 초과였다.
  - 전체 문서 smoke D2("10월 5일에 시작한 외부교육의 1회 과정 지원 한도"): 모델이 검색하지 않고 빈 되묻기를 냈고, 서버가 교육 되묻기 문구("어떤 교육을…")를 내보냈다. 3회 모두 재현, 8개 시험 corpus에서도 같음.
  - Wiki 빌드 첫 36 page 중 12개 미게시, 12개 모두 "주장 수 초과"(상한 14). 인용 위조는 3건뿐.
- **원인:**
  - 스키마 한도는 요청 하나에 담긴 도구 전체의 합이다. 문서 검색 권한과 티켓 권한을 둘 다 가진 일반 직원만 6개 도구를 받는데, 지금까지의 실제 smoke는 권한이 한쪽씩인 계정이었고 E2E는 가짜 모델이었다. 그래서 운영의 가장 흔한 계정에서만 깨졌다.
  - 빈 첫 답 재호출(D-37)이 빈 되묻기를 대상에서 뺐다(교육 되묻기 문구로 채우는 TS-19 설계). 규정 질문의 빈 되묻기에도 교육 문구가 나갔다.
  - 주장 수 상한을 "검사 실패"로 다뤘다. 원문과 어긋난 것이 아닌데 page 전체를 버렸다.
- **해결:** 처음에는 null 허용 선택 인자를 필수로 바꿔 한도를 맞췄다(선택 16·union 14). 그런데 dev 실행에서 모델이 필수가 된 `top_k`를 매번 채워(대부분 5) 원문 후보가 20개에서 5개로 줄었다. 비교 프로토콜 조건이 깨져 그 실행 3개(사용량을 아는 run 기준 공시가 $0.3164, 사용량 미확인 run 1개 별도, 실측)는 무효로 두었다. 최종 방식: 스키마 내용은 그대로 두고, strict 도구 합계가 한도를 넘으면 선택 인자가 가장 많은 도구(티켓 초안)만 strict를 끈다(나머지 5개 strict 합계 선택 17·union 10). strict를 끈 도구도 MOD-03이 같은 Pydantic 모델로 검증한다. 빈 되묻기도 강제 재호출(D-52). Wiki는 앞 14개 주장만 대조해 쓰고 잘린 수를 기록한다.
- **검증:** 같은 문항 실제 호출 200, 원문 후보 20개, 재호출 없음. 문서 6·교육 8 smoke 14/14(공시가 $0.0227), 티켓 smoke 3/3(티켓 초안 strict 해제 뒤). 시험: 6개 도구 요청이 한도 안이고 스키마 내용 그대로, 티켓 초안만 strict 해제, 문서만 받는 계정은 모두 strict, 빈 되묻기 강제 재호출, 주장 초과 잘라 쓰기. 백엔드 시험 680개 통과.
- **배운 점:** 공급자 제한은 요청 단위 합계로 걸린다. 한도를 맞추려고 스키마의 선택·필수를 바꾸면 모델 행동이 바뀐다(선택 인자를 필수로 만들면 모델이 값을 지어 채운다). 의미를 바꾸지 않는 쪽(검증 위치 이동)을 먼저 고른다. 권한 조합마다 도구 목록이 달라지면 "가장 많은 도구를 받는 실제 계정"으로 실제 호출을 한 번은 해 봐야 한다. 시험의 가짜 모델은 공급자 문법 한도를 재현하지 못한다.

## TS-34 dev 실측: 답해야 할 날짜 질문을 서버가 되묻기로 막음

- **맥락:** 100개 corpus로 dev A/B(50문항)를 처음 실제 모델로 돌렸다. 날짜 근원 검증(P-17, D-24·D-38)은 모델이 낸 날짜 인용을 서버가 사용자 문장과 대조하고, 목록 밖 표현은 되묻게 한 보수적 설계였다.
- **증상(실측):** A(예산 4000) 규칙 정답 0.44, 오답 28개 중 12개가 "답해야 할 질문에 되묻기". 다수가 서버 날짜 검증 거절이었다. "11월 12일부터 1박 2일로 대전 출장을 가는데" → 범위로 거절, "11월 6일 결재 건인데" → 시제 없음, "영상 끝까지 틀어 두었는데" → "까지"를 범위로 오인.
- **원인:** 목록이 시험용 문장(출발한·출발할)에 맞춰져 있었다. 실제 사용자 말투(가요·가는데·열리는·자로 발령)와 시제가 없는 질문을 모두 되묻기로 보냈다. 범위 판정은 문장 어디든 "까지"가 있으면 걸렸다.
- **해결(D-56, v5):** 시작 기준의 "M월 D일부터"는 시작일로 받고, 범위는 날짜 바로 뒤의 부터·까지만 본다. 자연 표지를 더했다. 시제가 없으면 오늘 ±90일 안의 연도 후보가 하나일 때만 정한다. 시제가 섞이면 되묻고, 사건 동사 밖에 과거 어미가 있으면 지난 후보만 본다("11월 3일 교육 참가는 했는데"에 올해 11월을 고르지 않게).
- **독립 검증에서 다시 깨짐:** 첫 v5를 검증 에이전트가 반례 46건으로 공격했고 19건이 **틀린 날짜를 조용히 verified**로 냈다(v4에서는 17건이 되묻기). 창 규칙은 "지난 12월 5일"·"쓴 택시비"·"25년 12월" 같은 과거 단서를 몰랐다. 새 표지 "열린"·"갔"·"받았"은 "열린다고"·"갔다 올"·"안내 받았"에도 걸렸다. 시작 기준의 "부터"는 다른 사건("11월 1일부터 재택근무하다가")에 붙어도 받았다. 표지 경계, 날짜 앞 "지난·다음", 과거 관형형, 두 자리 연도, 날짜와 사건 사이의 다른 사건 동사·절 끊김·다른 때, 이력 정정 검사로 고쳐 0건이 됐고, 46건 전부를 회귀 시험으로 고정했다. 이 사이 수정 전 코드로 돌던 dev 스윕은 멈추고 결과를 `dates-v5a/`로 분리했다.
- **2차 검증에서 또 깨짐:** 새 반례 76건 중 44건이 틀린 날짜였다. 이번에는 연도보다 위험한 **날 자체의 오류**가 섞였다("11월 2일 이후 출발하는"을 11월 2일 출발로, "11월 3일 아니고 5일"을 3일로, 이력의 "3일 출장" 뒤에 "4일로 바뀌었어요"가 와도 3일로). 목록을 덧대는 방식의 한계라, 날짜와 그 사건 사이를 구조로 검사하도록 바꿨다(연결어미·기준점·어림·다른 때·일만 있는 날짜가 끼면 되묻기, 신청 기준에서 다른 사건 명사면 되묻기, 이력 인용 뒤 정정 검사). 과거 단서는 강·약으로 나눠 약한 단서("지정한 과정")가 예정 질문을 막지 않게 했다. 1·2차 반례 122건 모두 틀린 날짜 0, dev 날짜 질문 모의 15/18 유지. 멈춘 스윕의 bash 반복이 자식 실행을 계속 띄운 것도 이때 발견해(`uv.exe`·`python.exe`까지 종료) 결과를 `dates-v5b/`로 분리했다.
- **과적합 방지:** dev만 보고 고쳤다. 이미 시작한 holdout 실행은 결과를 보기 전에 멈추고 `unseen-stopped-holdout-*`로 분리했으며, 동결을 풀고 v5 뒤에 holdout을 처음부터 다시 돈다.
- **검증:** dev 날짜 질문 18개 모의에서 날짜를 정한 수 7 → 15, 틀린 날짜 0(실측, 모델 호출 없음). 날짜 시험 205개(1·2차 검증 반례 113건 포함), 백엔드 시험 818개 통과. 변이 37개(창 규칙·강약 과거 단서·형용사 제외·전언 제외·섞인 시제·"부터"와 끝 날짜·연결어미·다른 때·앞쪽 사건 동사·다른 사건 명사·"지난·저번·다음·미리"·두 자리 연도·이력 정정·부정 예정·물결·근무지 등) 모두 시험이 잡음.
- **배운 점:** 재현율을 올리는 규칙(창 규칙)은 "틀린 날짜 0"을 dev 몇 문장으로 확인하는 것으로는 부족했다. 반례를 만드는 검증자를 따로 두어야 했다. 되묻기 쪽으로 기운 검증은 안전해 보이지만 정답률을 직접 깎는다. 실제 문항으로 재현율을 재고, 고칠 때는 "틀린 날짜 0"을 같이 확인한다. 평가셋 분할(dev로 고치고 holdout으로 잰다)을 지키려면 holdout 결과를 보기 전에 멈추는 절차가 필요하다.
