<a id="adr-01"></a>
## ADR-01 모듈형 모놀리스와 의존 방향 자동 검사

- **맥락:** 12개 모듈이 한 프로세스·한 DB에 있다. 같은 DB라는 이유로 다른 모듈의 테이블을 직접 읽기 시작하면 경계가 금방 무너진다.
- **결정:** 모듈 지도의 "허용 의존" 표를 테스트가 문서에서 직접 읽어 import를 검사한다. 공급자 SDK(anthropic, google)는 MOD-07만 쓴다.
- **버린 대안:**
  - 마이크로서비스: 배포·운영 비용에 비해 학습 목표가 흐려진다.
  - 규칙을 문서로만 두기: 위반을 알아챌 수단이 없다.
- **결과:**
  - 모델에 보여 줄 도구 명세 타입(`ToolSpec`)을 MOD-07에서 공통 계약(`shared`)으로 옮겼다. MOD-03은 MOD-07을 import할 수 없기 때문이다.
  - MOD-01은 MOD-04를 import할 수 없다. 그래서 교육 사본을 MOD-04에 묻지 않고 receipt로 검증한다([ADR-08](#adr-08)).
- **근거:**
  - 처음 만든 검사기는 `from agent.modules import x`와 상대 import를 놓쳤다(독립 검증이 찾음). 보강 후 금지 예시 10종을 넣어 모두 잡는지 확인한다.
  - 허용 표를 손으로 옮겨 적던 방식을 문서 파싱으로 바꿨다. 이때 `CP-06/07`처럼 설명 칸에 섞인 숫자를 모듈 ID로 읽지 않도록 했다.

<a id="adr-02"></a>
## ADR-02 비동기 서버 스택

- **맥락:** 한 요청이 모델 응답을 최대 60초 기다린다. 동기 서버는 그동안 작업자를 붙잡는다.
- **결정:** [D-28](../10-decisions-and-open-questions.md) 참고.
- **결과(실제로 치른 비용):**
  - psycopg async가 Windows 기본 이벤트 루프를 지원하지 않아 uvicorn·Alembic·pytest 모두 Selector 루프를 지정해야 했다([TS-07](troubleshooting.md#ts-07)).
  - 접속 시간 제한이 없으면 OS 재시도로 130초 멈췄다([TS-06](troubleshooting.md#ts-06)).
  - 비동기 ORM의 지연 로딩 오류를 피하려고 SQLAlchemy Core를 쓴다.

<a id="adr-03"></a>
## ADR-03 답변 Haiku 5.5, 임베딩·judge Gemini, thinking 끔

- **맥락:** 개인 예산으로 진행한다. Anthropic은 임베딩 모델을 제공하지 않는다.
- **결정:** 모델 구성은 [D-25](../10-decisions-and-open-questions.md)·[D-27](../10-decisions-and-open-questions.md)·[P-08](../15-policy-options.md) 참고. 추가로 Haiku 5.5의 thinking을 끄고 시작했다(2026-10-17 사용자 결정).
  - thinking 토큰에도 출력 요금이 붙는다.
  - thinking을 켜면 도구 왕복마다 thinking 블록을 원본 그대로 되돌려 보내야 해서 공급자 중립 메시지 계약이 복잡해진다.
- **버린 대안:**
  - thinking을 켜고 시작: 품질 이득이 측정되기 전에 비용과 계약 복잡도를 먼저 지게 된다.
  - judge도 Haiku: 자기 답을 선호할 위험이 있다(P-08).
- **결과·근거:**
  - thinking을 끈 상태에서 smoke 6/6이 통과했다(프롬프트 수정 후, [TS-01](troubleshooting.md#ts-01)).
  - 실패 1건(0건 시나리오)은 thinking이 아니라 프롬프트로 해결됐다. 다만 thinking을 켜면 해결되는지는 비교하지 않았다.
  - **다시 볼 조건:** 도구 선택 오류가 smoke·dev 평가에서 반복될 때.

<a id="adr-04"></a>
## ADR-04 재시도는 한 곳에서만: SDK 자동 재시도 끔

- **맥락:** Anthropic Python SDK는 기본적으로 429·5xx·연결 오류를 2회 재시도한다. 실행 상한은 "모델 시도 6회(재시도 포함)"다.
- **결정:** SDK 재시도를 끄고(`max_retries=0`), 재시도 판단은 MOD-02 한 곳에서만 한다. 논리 호출당 1회다.
- **버린 대안:** SDK 재시도를 그대로 쓰기. 바깥 상한이 6회여도 안쪽에서 회당 최대 3번 시도하므로 실제 시도는 최대 18회가 될 수 있다. 이 18회는 설정값으로 계산한 상한이고 측정한 값은 아니다.
- **근거:**
  - 실제 클라이언트의 `max_retries == 0`을 테스트한다.
  - 검증 에이전트가 SDK 1.15 소스(`_base_client`)에서 재시도 루프가 0회인 것을 확인했다.
  - SDK 재시도를 다시 켜는 mutation을 넣으면 테스트가 잡는다(검증 에이전트 실행).

<a id="adr-05"></a>
## ADR-05 모델 출력은 서버가 결과 원장과 대조해 확정

- **맥락:** 모델은 그럴듯한 교육 ID나 "없습니다"를 지어낼 수 있다. JSON 스키마는 형식만 보장한다.
- **결정:** 최종 답의 `training_ids`·선택값은 이번 실행의 도구 결과 또는 검증된 사본에 있어야 한다. outcome도 실제 기록과 맞아야 한다.
  - `no_results`: 성공한 목록 조회가 있을 때만 인정
  - 되묻기: 선택값을 저장하지 않음
  - 아직 없는 기능의 outcome(`action_pending`): 거절
- **버린 대안:**
  - 프롬프트로만 막기: 실제로 "확인 중입니다"가 형식 검증을 통과했다([TS-01](troubleshooting.md#ts-01)).
  - 무효 출력이면 모델에게 다시 시키기: 명세가 "무효 출력은 실패"로 정했고, 비용 상한도 흐려진다.
- **근거:**
  - 지어낸 ID 거절과 원장 검사를 지우는 mutation을 테스트가 잡는다.
  - outcome 검사는 독립 검증에서 빈틈이 발견돼 보강했다([TS-04](troubleshooting.md#ts-04)).

<a id="adr-06"></a>
## ADR-06 메시지 멱등 수락: 행 잠금 + 부분 유일 인덱스

- **맥락:** 브라우저는 응답을 잃으면 같은 메시지를 다시 보낸다. 실행이 두 번 돌면 비용이 두 배가 되고 상태가 꼬인다. 실행 계약은 같은 키·같은 내용이면 같은 run, 다른 실행 중이면 409로 정했다([D-13](../10-decisions-and-open-questions.md)).
- **결정:**
  - 수락은 대화 행을 잠근(`SELECT … FOR UPDATE`) 한 트랜잭션에서 한다. 순서는 만료 회수 → receipt 확인 → 활성 run 확인 → 메시지·run·receipt·활성 소유권 저장이다.
  - DB에는 "대화당 running run 하나"인 부분 유일 인덱스를 둔다.
  - 모델·도구를 기다리는 동안에는 잠금을 잡지 않는다.
- **버린 대안:**
  - 애플리케이션 메모리 잠금: 프로세스가 여러 개면 무력하다.
  - 인덱스만 두기: 정상 경로가 예외 처리에 기대게 된다.
- **근거(가짜 모델, 테스트 DB):**
  - 같은 대화에 메시지 5개를 동시에 보내면 200 한 개, 409 네 개, run 1개가 남는다.
  - 같은 키 재전송은 모델 호출 0회 추가이고, 같은 키·다른 내용은 409다.
  - mutation 5종 중 4종을 테스트가 잡았다. "코드의 활성 run 검사 제거"는 잡히지 않았는데, 부분 유일 인덱스가 같은 409를 내기 때문이다. 이중 방어가 실제로 동작한다는 근거로 남긴다.
- **검증 뒤 보강:** 독립 검증에서 수락과 만료 회수의 잠금 순서가 반대라 교착이 재현됐다([TS-16](troubleshooting.md#ts-16)). 지금은 모든 쓰기 경로가 "대화 행 → run" 순서로 잠근다.

<a id="adr-07"></a>
## ADR-07 큐 없이 요청 안에서 실행하고 연결 끊김에서 보호

- **맥락:** 명세는 최초 응답을 동기 200으로 정했고, 응답 유실이나 클라이언트 timeout을 서버 취소로 보지 않는다. 큐·스케줄러는 추가하지 않는다([실행 계약](../contracts/01-run-lifecycle.md)).
- **결정:** 실행을 별도 asyncio task로 띄우고 요청은 `asyncio.shield`로 기다린다. 요청이 취소돼도 실행과 완료 commit은 계속된다. 결과는 같은 키 재전송으로 받는다.
- **버린 대안:**
  - 작업 큐(Celery 등): MVP 범위에서 운영 요소만 늘어난다.
  - 요청 코루틴에서 직접 실행: 연결이 끊기면 실행도 취소된다.
- **결과:**
  - 프로세스가 죽으면 실행도 사라진다. 이는 영속 deadline과 다음 진입 시 만료 회수로 처리한다.
  - 최종 commit이 실패하면 성공도 202도 아닌 503으로 응답한다([TS-11](troubleshooting.md#ts-11)은 시작 회수를 백그라운드로 옮긴 관련 사례).

<a id="adr-08"></a>
## ADR-08 검증된 대화 사본만 모델 문맥에

- **맥락:** "그중 보안교육 장소는?" 같은 후속 질문에는 이전 결과가 필요하다. 그런데 이전 답변 문장은 모델이 쓴 글이라 근거가 될 수 없다. 저장된 업무 상태도 조작되거나 실패한 실행의 것일 수 있다.
- **결정:** 다음 턴 모델 문맥에는 "대화 자료"만 넣는다. 이 대화의 **완료된** run이 남긴 실제 교육 receipt와 ID·시작 시각이 맞는 사본만 해당한다. 프롬프트 규칙은 이전 답변 문장을 근거에서 뺐다. CP-07 읽기 포트의 최소형이다([D-15](../10-decisions-and-open-questions.md)).
- **버린 대안:**
  - 이력 텍스트만 넘기기: 모델이 이전 문장을 사실로 재사용한다.
  - 매번 다시 조회: 후속 질문마다 도구 호출 비용이 든다.
- **근거:** receipt 없이 업무 상태만 조작한 경우 사본이 문맥에 들어가지 않고 그 교육을 말하면 실패한다(테스트). 다른 대화나 실패 run의 receipt, 시작 시각이 다른 사본도 쓰지 않는다. 사본 검증을 생략하는 mutation을 테스트가 잡는다.
- **검증 뒤 보강:** 처음 구현은 receipt만 봤고 현재 권한은 다시 보지 않았다. 그래서 권한 없는 사용자의 문맥에도 사본이 들어갔다([TS-17](troubleshooting.md#ts-17)). 지금은 사본도 현재 권한으로 거르고, 가림 판정은 문맥에 들어간 의존 자원 전체로 한다.
- **열린 질문:** 이 읽기를 명세처럼 MOD-02에 포트로 주입할지([P-12](../15-policy-options.md)), 자료를 system에 둘지([P-13](../15-policy-options.md))는 미정이다.
- **남은 일:** 실제 모델로 후속 질문 흐름을 확인하는 smoke는 준비만 했고 아직 실행하지 않았다(과금, 승인 대기).

<a id="adr-09"></a>
## ADR-09 답변 본문은 검사 후 한 번에, 스트리밍은 진행 상황만

- **맥락:** 토큰 스트리밍은 체감 속도가 가장 빠르다. 하지만 이 서비스는 답을 보여 주기 직전에 권한을 다시 확인하고 인용을 결과와 대조한다.
- **결정·대안 비교:** [P-09](../15-policy-options.md), [D-29](../10-decisions-and-open-questions.md) 참고. 면접에서 설명할 핵심은 "흘려보낸 글자는 되돌릴 수 없다"는 점이다. 검사 전에 보낸 내용은 나중에 권한이 없다고 판정돼도 이미 화면에 나간 뒤다.
- **구현:** 같은 메시지 POST에 `Accept: text/event-stream`을 붙이면 SSE로 응답한다. 새 경로를 만들지 않아 멱등키·수락·409·replay 규칙을 그대로 쓴다.
  - progress에는 `{run_id, seq, stage}`만 넣는다. stage는 닫힌 7개 값이고, 도구 인자·제목·결과 수는 받는 자리부터 없다(결과 수도 제한 문서의 존재를 짐작하게 한다).
  - 실행은 요청과 분리된 task라 연결이 끊겨도 계속된다([ADR-07](#adr-07)). UI는 GET run 뒤 같은 키 replay로 결과를 받는다. 실행 중 replay는 SSE를 다시 열지 않고 JSON 202다.
  - 단계 기록은 필수 기록이 아니다. 기록이 실패해도 실행을 멈추지 않는다. 반대로 도구 기록·교육 receipt는 실패하면 실행을 멈춘다(CT-11).
- **검증:** 가짜 모델 테스트 18개, mutation 17종 모두 잡힘. 실제 서버(uvicorn)에서 단계가 실제로 나눠 도착하는 것을 확인했다. 예: accepted 0.09s → training_lookup 1.98s → verifying 3.48s → result 3.56s(실제 모델 1회).
- **상태:** 구현. 화면 표시는 UI 연결 때.

## ADR-10 근거 개수 고정 상한 대신 token 예산

- **맥락:** 초기 명세는 "최종 근거 최대 5개"였다. 사용자가 "필요한 근거가 잘리면 어떡하냐"고 이의를 제기했다.
- **결정:** [D-20](../10-decisions-and-open-questions.md)·[D-21](../10-decisions-and-open-questions.md)·[P-03](../15-policy-options.md) 참고. 근거가 된 연구는 [참고 자료](../11-references-and-portfolio.md)의 "근거 양·예산 참고"에 있다(Lost in the Middle 등).
- **상태:** 결정만 했다. 적정 예산은 M3 dev 예산 스윕으로 측정한다. 지금은 성능 이득을 주장하지 않는다.

<a id="adr-11"></a>
## ADR-11 과금 호출 통제 장치

- **맥락:** 개인 예산이다. 테스트 중 실수로 유료 호출이 반복되면 안 된다.
- **결정:**
  - CLI `ask`는 기본이 dry-run이다. 보낼 요청만 출력하고 호출하지 않는다.
  - 실제 호출은 `--live`를 명시할 때만 한다.
  - 실제 모델 테스트(`-m live_model`)는 기본 pytest에서 제외된다.
  - 실행마다 실제 토큰과 공시 가격 기준 금액을 저장소 밖 파일에 남긴다.
  - 사용량을 일부라도 모르면 금액을 계산하지 않는다(모르는 비용을 0원처럼 보이지 않게).
- **근거:**
  - 2026-10-17 실제 호출 누적은 입력 70,940 / 출력 3,237 토큰, 공시 가격 기준 약 $0.0087이다. Console 청구액과 대조하지 않았다.
  - 계획 단계의 예측(smoke 1회 $0.01~0.03)보다 실측(6개 $0.0027~0.0034)이 작았다.
  - dry-run이 [TS-09](troubleshooting.md#ts-09)를 비용 없이 잡았다.

<a id="adr-12"></a>
## ADR-12 AI가 쓴 코드의 검증 절차

- **맥락:** 코드와 테스트를 같은 AI 작성자가 쓰면 같은 맹점을 공유한다. 실제로 아무것도 검증하지 않는 테스트를 작성 중 여러 번 썼다(계산식만 보는 테스트, `if False else None`, 이전 실행의 DB 행을 읽고 통과하는 테스트).
- **결정:** 단계마다 다음을 한다.
  1. 작성자와 분리된 읽기 전용 검증 에이전트를 돌린다. 파일 수정·과금 호출·`.env` 접근을 금지하고, 주장마다 실행했는지 추론했는지 표시하게 한다.
  2. 보고를 그대로 믿지 않고 핵심 주장을 직접 재현한다.
  3. 고친 뒤 결함을 일부러 넣는 mutation으로 테스트가 실제로 잡는지 본다.
  4. 수정 전 커밋에 새 테스트를 돌려 실패하는지 본다.
  5. 실제 서버·실제 모델(승인 후)로 테스트 밖 동작을 확인한다.
- **근거:**
  - M0·M1 검증에서 P2 12건을 찾았다(P1 0건). 그중 핵심 7건을 직접 재현했다.
  - 보강한 테스트를 수정 전 커밋에 돌리자 38개가 실패했다.
  - 실서버 확인이 테스트가 놓친 결함 2건을 찾았다([TS-12](troubleshooting.md#ts-12)).
  - M2 검증에서는 테스트 258개가 모두 통과한 상태에서 mutation 33종 중 24종이 생존했다(검증 에이전트 실행). 테스트를 보강한 뒤 다시 돌려 32종 중 31종을 잡았다. 남은 1종은 동등 mutation이다([TS-18](troubleshooting.md#ts-18)).
  - 검증 도구 자체도 검증한다. 처음 쓴 교착 테스트는 잠금을 쥐기 전에 멈춰서 결함을 잡지 못했다([TS-16](troubleshooting.md#ts-16)).
  - 검증 에이전트의 제안을 그대로 받지 않은 경우도 기록한다. 예: "0건일 때만 no_results 허용" 제안을 "성공한 조회가 있을 때"로 바꿨다([TS-04](troubleshooting.md#ts-04)).
