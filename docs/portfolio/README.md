# 포트폴리오 기록

사내 업무 도우미를 만들며 내린 결정과 실제로 겪은 문제를 면접·포트폴리오에 쓸 수 있게 정리한다.

| 문서 | 내용 |
|---|---|
| [ADR](adr.md) | 결정마다 맥락·버린 대안·결과·근거. 결정 자체는 [D 표](../10-decisions-and-open-questions.md)·[P 선택지](../15-policy-options.md)에 링크로만 연결한다 |
| [트러블슈팅](troubleshooting.md) | 사례마다 증상·재현·원인·해결·검증·커밋 해시 |

## 작성 규칙

- 숫자는 이 저장소에서 실행해 얻은 값만 쓴다. 테스트 시간·토큰·금액·통과 수에는 출처(명령·커밋)가 있어야 한다.
- 별도로 실행한 검증 에이전트의 결과는 "검증 에이전트 실행"이라고 표시한다. 추정이나 해석은 "추정"이라고 적는다.
- 금액은 실제 토큰 × 공시 가격으로 계산한 값이다. Console 청구액과 대조하지 않았으면 그렇게 적는다.
- smoke 통과는 소수 시나리오 확인이다. "정확도", "유출 0", "비용 절감"처럼 평가가 필요한 표현은 평가 결과 없이 쓰지 않는다([참고 자료](../11-references-and-portfolio.md)의 원칙).
- 아직 커밋하지 않은 변경의 사례는 "커밋 후 기입"으로 두고, 커밋하면 해시를 채운다.

## 면접에서 이야기하기 좋은 순서(제안)

1. [TS-01](troubleshooting.md#ts-01): 모델이 형식은 맞지만 내용이 빈 답을 낸 문제. 원인을 기록할 수단부터 만들고 재현·수정·재측정한 과정과 비용.
2. [TS-02](troubleshooting.md#ts-02) + [ADR-12](adr.md#adr-12): 테스트가 결함을 못 잡는다는 것을 mutation으로 확인하고, 수정 전 커밋에서 새 테스트가 실패하는지로 검증한 과정.
3. [ADR-05](adr.md#adr-05) + [ADR-09](adr.md#adr-09): LLM 출력을 서버가 확정하는 이유, 토큰 스트리밍을 하지 않는 이유.
4. [ADR-06](adr.md#adr-06) + [ADR-07](adr.md#adr-07): 응답 유실·동시 요청에서 실행을 한 번만 하는 설계와, mutation으로 확인한 이중 방어.
5. [TS-03](troubleshooting.md#ts-03): 테스트 DB 보호 우회처럼 독립 리뷰로 찾은 데이터 안전 문제.
