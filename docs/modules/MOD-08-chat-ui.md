# MOD-08 업무 대화 화면


## 책임과 소유권

사용자의 대화 선택·입력·교육/티켓/원문 표시·티켓 확인 UI 상태를 소유한다. 업무의 기준 데이터·서버 세션·권한·LLM 키는 소유하지 않는다. 통합 업무지원 정적 시안은 있으나 실제 HTTP/AI 연결 완료가 아니다.

## 공개 협력

MOD-01 대화/메시지/run, MOD-04 교육 상세, MOD-05 근거/PDF, MOD-09 세션, MOD-12 티켓/action 상태/수정 재준비/확인을 HTTP로 사용한다. SDK·DB·Wiki 관리 API를 직접 사용하지 않는다.

## 화면 계약

- PC: 대화 목록 + 중앙 업무 대화 + 선택적 상세/출처. 모바일: 메뉴·전체 너비 상세·뒤로 복귀.
- 인용: 문서명·판본·조회 기준일·실제 PDF 페이지·원문 구간. 과거 판본임을 구분한다.
- 티켓: 준비된 subject/description/category·만료·확인/취소. 확인 누름 전에는 등록 완료 문구 금지.
- 편집은 최초 action_pending을 바인딩한 폼이다. draft는 변경이 없어도 version/fields/멱등키로 revise하여 pending을 만든다. pending은 변경 없으면 GET action, 변경하면 revise를 호출하고 새 action의 preview를 확인한다. 새로고침 후 이전 메시지의 action은 current_action_id를 따라 새 내용을 다시 표시하며 자동 승인하지 않는다. 확인 요청에는 fields를 재전송하지 않는다. 자유문장은 사용자 입력으로 표시하며 검색 원문을 자동 첨부하지 않는다.
- 확인 중 반복 전송을 막고 동일 Idempotency-Key를 재사용한다. 응답 유실이면 action 상태를 조회한다.
- 메시지 전송과 수정 재준비에도 각각 입력당 생성한 멱등키를 유지한다. running replay202는 같은 키/본문을 보관한 채 GET run으로 종료를 확인하고 동일 POST replay로 최종 answer/citations/action_preview를 받는다. 새 키/새 메시지로 보내지 않는다.
- 과거 답변 재열람은 서버의 재검증 결과를 따른다. 제한 자원이면 로컬 캐시도 제거하고 일반 안내 표시.
- 동기 메시지 POST 동안은 처리 중만 표시한다. 서버가 보내지 않은 도구 실행 단계나 스트리밍을 연출하지 않는다.
- 0건·추가 질문·근거 부족·실패·권한 만료를 구분한다. 서버 비밀·trace 내부 본문 노출 금지.
- 상태를 수동 선택하는 직원 메뉴는 두지 않는다. 첫 화면에서 질문으로 시작하고 응답 상태를 대화 안에 표시한다. 입력 식별 경계는 인접 배경과3:1 이상이며 포커스도 유지한다.

## 검토·테스트

## 2026-10-17 계약 보정

draft 폼과 pending 확인을 구분한다. 편집 진입/취소는 pending을 변경하지 않고 revise 성공만 교체한다. form은 message ID로 바인딩하며 입력 중 값·대화별 composer를 보존한다. expired/cancelled/superseded를 편집으로 되살리지 않는다.

편집은 action ID와 message ID에 바인딩하며 해당 폼에 포커스를 둔다. 충돌 거절에서 입력을 보존하고 현재 head를 조회한다. 만료 후 확인은 명시적인 미접수 안내와 새 준비 경로를 제공한다. 다른 대화에서 확인이 끝나면 완료 알림과 해당 대화 표시를 보존하며 복귀 시 현재 상태로 재조회한다.
