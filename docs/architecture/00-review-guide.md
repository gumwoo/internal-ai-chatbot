# 설계 검토 안내

## 검토 범위

이 명세는 **인프라 → 애플리케이션 → 레이어 → 모듈 → 모듈 협력**까지 정의한다. 모듈 문서의 공개 작업 이름은 의미 계약이며 실제 Python 함수명이나 클래스 구조를 강제하지 않는다. 내부 구현은 [구현 참고](../implementation-notes/README.md)로 분리한다.

## 순서

1. [프로젝트 범위](../00-project-overview.md), [요구사항](../01-requirements.md).
2. [인프라](01-infrastructure.md) → [애플리케이션](02-applications.md) → [레이어](03-layers.md).
3. [모듈 지도](04-module-map.md)에서 소유권·허용 의존성을 확인한다.
4. MOD-09 권한, MOD-04 교육, MOD-07 모델, MOD-03 도구, MOD-02 실행, MOD-01 대화를 검토한다.
5. MOD-05 원문, MOD-06 수집, MOD-10 Wiki, MOD-11 검색 전략을 묶어 검토한다.
6. MOD-12 티켓과 MOD-08 화면을 [협력 시나리오](05-collaboration.md)로 확인한다.
7. [공통 계약](../contracts/00-shared-contracts.md), [API](../04-api-spec.md), [테스트](../07-test-and-evaluation.md)의 경계가 일치하는지 확인한다.

## 모듈별 확인 항목

- 무엇을 소유하고 어떤 쓰기 작업만 허용하는가?
- 공개 작업의 입력·출력·실패·권한·원자성은 명확한가?
- 필요한 데이터는 소유 모듈의 계약으로 얻는가?
- 재시도·시점·권한·기록·commit 책임이 한 곳에 있는가?
- 성공과 실패를 어떤 테스트로 관찰하는가?

## 개정 2의 차이

8개 모듈을 12개로 확장했다. 기존 교육 모듈은 유지하고 PDF·ACL·시점·Wiki·검색 전략·IT 티켓을 추가했다. 과거의 전사 공개 문서·현행본만 조회·조회 전용 전체 MVP라는 가정은 폐기했다. 교육 정적 시안과 구현 예제는 이전 범위 자료임을 표시한다.

## 문서가 충돌할 때

프로젝트 범위/요구사항 → 의미별 기준 문서 → 모듈 공개 계약 → 구현 참고 순으로 본다. HTTP는 API, DTO는 공통 계약, 문서 정책은 메타데이터 계약, A/B는 비교 프로토콜, 티켓은 티켓 흐름이 기준이다. 충돌을 발견하면 구현 편의로 고르지 말고 관련 기준 문서를 함께 수정한다.
