# 애플리케이션 레이어

레이어는 모듈보다 큰 업무 구분이 아니라 각 모듈 내부의 책임 구분이다. 모든 모듈에 동일한 수의 폴더·클래스를 만들 필요는 없다.

| 레이어 | 책임 | 허용 | 금지 |
|---|---|---|---|
| 진입 어댑터 | HTTP·CLI·도구 스키마·세션 입력·응답 변환 | 공개 유스케이스 호출 | SQL·모델 SDK·권한 추정 |
| 애플리케이션 | 요청 수락·검색 전략·실행/게시/확정 조정 | 업무 계약·포트 호출, 트랜잭션 경계 | 타 모듈 테이블 접근 |
| 업무 정책 | 날짜·판본·접근·멱등성·유효성 불변식 | 공급자 중립 타입·규칙 | HTTP·SDK·ORM 객체 의존 |
| 외부 어댑터 | DB·SDK·파일·파서·관측 구현 | 상위가 요구한 포트 구현 | Agent의 업무 의사결정 소유 |

의존은 진입 → 애플리케이션 → 업무 정책/포트로 향한다. DB·SDK 어댑터는 포트를 구현해 조립 지점에서 주입한다. 계약상 observer 호출과 구체 모듈 import는 구분한다.

## 모듈 협력과 레이어

- MOD-03 도구와 교육 HTTP는 MOD-04의 같은 공개 조회 작업을 사용한다.
- MOD-11은 MOD-05·MOD-10의 공개 검색/원문 계약으로 조정하며 저장소를 공유하지 않는다.
- MOD-09는 판정 정책을 소유하고 문서·티켓 소유 모듈이 자원 ACL을 전달한다.
- MOD-02는 결과 후보와 관측 이벤트만 반환한다. 대화 DB 커밋은 MOD-01이 한다.
- 티켓 확인 HTTP는 MOD-12로 직접 들어간다. LLM의 승인 문구를 서버 승인 이벤트로 변환하지 않는다.

공개 계약을 검토한 뒤 내부 함수·폴더·SQL을 선택한다. SQL 예제의 존재가 모듈 경계를 우회할 근거가 되지 않는다.
