# 프로젝트 범위와 완료 기준

설계 개정 2 · 2026-10-16. 이전 교육 조회 중심 설계를 통합 업무지원 범위로 대체한다. 기존 모듈 ID와 교육 조회 계약은 유지한다.

## 목표

가상 회사 직원이 자연어로 사내 규정을 확인하고 교육 일정과 IT 지원 업무를 처리한다. 개발 관점의 핵심은 도구 선택, 대화 상태, 원문 근거, 권한, 개정 대응, 실패 추적이다. 모델 학습·GPU 서빙을 이번 프로젝트의 중심으로 삼지 않는다.

## 최종 MVP

| 영역 | 포함 |
|---|---|
| 대화 | 소유권·후속 질문·모호성 처리·실행 제한·실패 기록 |
| 원문 지식 | 사용자 PDF 100개, 원본 보존·파싱·청크·벡터·페이지 출처 |
| 개정 | 91개 논리 문서, 현행 91파일·이전 판본 9파일, 특정 날짜 조회·전후 비교 |
| 권한 | 로컬 계정·세션, 문서 접근 통제, 대화·근거·캐시 재검증 |
| Wiki | 출처별 주장·관계 정리, 생성·검수·게시·갱신 상태, 원문 회수 연결 |
| 업무 도구 | 교육 목록·상세, IT 티켓 목록·상세·등록 준비 |
| 업무 변경 | 사용자 확인 API로만 IT 티켓 생성, 멱등 처리·감사 기록 |
| 실험 | 동일 조건 A 원문 RAG / B Wiki 보조 원문 RAG, 목표 150문항 |
| 화면·운영 | PC 우선 대화·출처·티켓 확인, Docker 재현, 단계별 로그 |

첫 구현 구간은 교육 조회만으로 작동을 검증한다. 100개 PDF 전체 처리·Wiki·티켓은 이후 단계의 필수 최종 범위다. 작은 파일 집합으로 먼저 검증해도 전체 완료로 보고하지 않는다.

## 입력과 산출물

- 사용자가 PDF와 문서의 규칙·시행일·버전·접근 정책을 제공한다. 제목 목록은 [문서 구성](corpus/00-document-inventory.md)을 따른다.
- 개발 산출물은 서비스·색인/Wiki 명령·검증 보고서·재현 가능한 실행 설정이다.
- 질문 150개는 제작 목표이며 지금 존재하거나 정답이 검수됐다는 뜻이 아니다.
- PDF·규정 본문·정답셋은 사용자 요청 없이 자동 제작하지 않는다.

## 의도적으로 제외한 범위

교육 신청·HR 신청/결재, 실제 계정·VPN 설정 변경, ITSM 전체 상태 관리, 완전한 노코드 Builder, MCP 도입, 멀티 Agent, Redis·Kafka·Kubernetes·모델 학습·GPU 운영은 후속 검토다. 로컬 데모의 인증 경계를 실제 기업 SSO 완료로 표현하지 않는다.

## 프로젝트 완료 판단

100파일 목록과 메타데이터를 검수하고, 권한·시점·원문 출처가 두 검색 방식에서 동일하게 지켜져야 한다. 티켓은 확인 전 생성되지 않고 중복 확인도 한 건만 만든다. 테스트와 150문항 평가를 실행해 질문 유형별 결과·실패 원인·온라인 및 구축 비용을 제시한다. Wiki 우위는 가정하지 않는다.
