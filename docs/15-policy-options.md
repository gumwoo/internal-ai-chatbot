# 3차 검토: 정책 선택과 사용자 확인 기록

상태: 2026-10-17 사용자 확인 반영. P-01은 B(독립 초안 여러 개+head 하나), P-02는 A(원규정 공백 시 규정 결론 보류)를 선택했다. P-03은 사용자가5개 고정 상한에 이의를 제기하고 필요한 근거 보존을 요구해 아래 수정 결정으로 대체했다. P-04는 B(전체 문맥 기준선만 먼저, 재정렬은 조건부 추가), P-05는 B(연도 시제 추론·표시), P-06은 A(수정 사슬 상한 없음), P-07은 A(모델 판단+측정, 조건부 C)를 선택했다. P-10·P-11은 M0·M1 독립 검증에서 나온 미정 항목이다(O-14·O-15). P-12~P-14는 M2 독립 검증에서 나온 미정 항목이다(O-16~O-18). 대안 표는 검토 이력이다.

## P-01 티켓 초안과 계보

| 선택 | 장점 | 비용·제약 |
|---|---|---|
| A. 대화당 root 하나, 후속 초안은 그 root 아래 | 계보 탐색 단순, 한 지원 건이라는 의미 명확 | 후속 초안의 출처 run과 이전 준비를 따로 기록해야 하며 분기/대체 관계는 여전히 필요 |
| B. 독립 root draft 여러 개, 확인 가능한 head 하나 | 기존 준비를 유지하며 새 내용을 검토, 현 시안의 여러 폼 사례와 일치 | root 간 head 교체를 표현하고 오래된 초안 충돌을 검증해야 함 |

확정: B. 단순 supersedes 한 필드 대신 `prepared_from_action_id`(직접 수정/소비한 draft 또는 pending)와 `displaced_head_id`(별도로 대체된 이전 pending)를 구분한다. 한 번에 임의 개수의 action을 대체하는 범용 기능은 제안하지 않는다. A를 선택해도 두 관계의 구분은 필요할 수 있다. 기존 root_action_id는 준비 출처를 의미하며 대화 전체의 유일 root라고 단정하지 않는다.

공통 불변식: 대화별 head row 하나, head_revision은 단조 증가, 처음 head row 생성도 같은 유일 경계에서 직렬화, 실패한 draft는 기존 pending 불변. cancel 뒤 head ID를 유지해 이력을 찾고 revision을 올리는 안을 기술 계약으로 채택한다. ID를 null로 비우는 대안은 별도의 last_action_id/세대 번호가 필요하다. head row 필드는 14번 문서의 기술 계약을 따른다.

## P-02 guidance 판본과 규정 공백

| 선택 | 장점 | 비용·제약 |
|---|---|---|
| A. 사건 적용 원규정이 없으면 규정 결론 보류 | FAQ만으로 금액/권리/의무를 잘못 확정하는 것을 방지 | 해설만 존재하는 질문에서 기권 증가 |
| B. 검수된 guidance만으로 제한적 안내 허용 | 안내 범위 확대 | 안내의 권위·예외·검수 기준을 추가로 확정해야 함 |

확정: A. guidance는 절차 안내 자료로 보여줄 수 있지만 규정 공백의 금액/권리/의무를 채우지 않는다. 최신 guidance 선택은 기본적으로 knowledge_as_of에서의 유효한 안내 판본을 고르고, 과거 가이드 자체를 요청한 경우에만 명시 판본을 고르는 방식이다. IT-045/046처럼 개정 쌍이면 단순 available_from 조건만으로 둘 다 답변에 넣지 않는다.

반대편 판본의 경과조항은 검수된 `transition_relations`로 필요한 조항만 보조 회수한다. 다른 판본 전체를 답변에 섞지 않는다. 해당 조항의 명시 사건 조건이 충족될 때만 적용하며 규정 충돌은 자동 해결하지 않는다. 이 회수 계약의 적용은 P-02 선택과 별개로 유지한다.

## P-03 평가 근거 수와 예산

| 선택 | 장점 | 비용·제약 |
|---|---|---|
| A. MVP 주 평가를 최소 충분 근거 집합이5 passage 이내인 문항으로 제한 | 기존 최종5 passage 예산과 정합, 비교 단순 | 어려운 종합 질문의 범위 제한을 공개해야 함 |
| B.5개 초과 근거 문항도 포함하고 별도 층으로 보고 | 실제 어려운 질문의 한계가 드러남 | 기존 상한에서는 완전 회수가 불가능할 수 있으며 성능 해석을 구분해야 함 |
| C. dev에서 공통 passage 예산을 늘린 뒤 동결 | 복합 질문의 답변 가능 범위 확대 | A/B 모두 비용·지연 증가, 새 실험 설정 필요 |

수정 결정: 최종 passage 수5개 고정 상한을 폐지한다. 필요한 원규정·조건·예외 근거를 보존하고 token 예산으로 문맥을 관리한다. gold를 줄이거나 초과 문항을 숨기지 않으며 budget_exceeding 층으로 보고한다. 주 표본과 초과 층의 구성·분모를 공개한다. 필수 근거의 단위는 문서 수와 구분하고 동일 parser/chunk 설정의 원문 anchor 및 최소 충분 passage 집합으로 기록하며 대체 근거 집합도 검수한다. 평가150문항 계획은 유지하고 최종 token 예산은 dev 검증 후 holdout 전에 공통 동결한다. 필요 근거를 모두 찾는다는 보장은 평가로 검증하며 임의로 주장하지 않는다.

선택과 무관하게 Wiki 주제·빌드/답변 프롬프트·모델·검색/병합 설정은 holdout 열람 전 hash로 동결하고 judge는 A/B 이름·경로를 보지 않는다. 이는 품질 평가의 기술적 통제이며 gold 제한 선택을 대신하지 않는다.

조사 반영(사용자 확인): 고정 개수 대신 token 예산을 쓰는 결정은 유지한다. 예산 값은 dev 예산 스윕으로 정하고, 회수는 Recall@pool/Recall@budget·evidence-in-context로 측정하며, packing_order를 고정한다(D-21, [비교 프로토콜](13-retrieval-comparison.md)).

## P-04 재정렬과 전체 문맥 기준선

상태: 2026-10-17 사용자 확인, B 선택. 아래 두 실험은 주 실험(A/B 벡터 비교)에 포함하지 않는다. 하나도 하지 않아도 주 실험 결론은 성립한다.

| 선택 | 장점 | 비용·제약 |
|---|---|---|
| A. 둘 다 하지 않음 | 범위·비용 최소, 주 실험에 집중 | 실무 표준(재정렬)과의 차이와 검색의 한계선을 설명할 근거가 없음 |
| B. 전체 문맥 기준선만 | 결과 해석의 기준점이 생김. 검색·재정렬이 없어 구현이 단순. 코퍼스가 248쪽으로 작음(실행 가능 여부는 token 실측 전 미확인, 예측) | actor별 허용 원문 token 실측 필요, 모델 입력 한도·모델 호출20초·run60초를 넘는 문항은 불가. 요청당 비용 큼 |
| C. 공통 재정렬 실험만 | 실무에서 흔한 구성과 비교 가능, hard negative 완화 여부 측정 | 한국어 reranker 선정·지연 추가, 2×2 실험으로 실행량 2배 |
| D. 둘 다 | 해석 근거가 가장 충분 | 비용·일정이 가장 큼 |

확정: B. 전체 문맥 기준선만 먼저 계획한다. 구현이 가장 단순하고, A/B 결과에 "검색을 더 잘하면 얼마나 오를 수 있는지"의 기준점을 주기 때문이다.

- 전체 문맥 기준선: 실행 전에 문항별 actor×사건 조합의 허용 원문 token 수를 같은 tokenizer로 실측한다. 모델 입력 한도·모델 호출20초·run60초 중 하나라도 넘는 문항은 infeasible로 기록하고 품질 점수와 분리한다. 이 경우 기준선을 위해 실행 상한이나 필터를 바꾸지 않는다. 조건과 지표는 [비교 프로토콜](13-retrieval-comparison.md)의 전체 문맥 기준선 절을 따른다.
- 공통 재정렬(C): 지금은 실행하지 않는다. dev 예산 스윕 결과에서 hard_negative anchor를 인용한 오답이 확인되면 사용자와 확인한 뒤 별도 비교 ID로 추가한다. 무엇을 "확인됨"으로 볼지의 판단 기준과 reranker 후보 수·모델·지연 허용치는 그때 O-12에서 정한다. holdout 결과를 본 뒤에 재정렬을 추가해 같은 평가 버전으로 보고하지 않는다.

결정은 D-22와 O-12에 기록한다.

## P-05 연도가 없는 날짜의 해석

| 선택 | 장점 | 비용·제약 |
|---|---|---|

### P-05 보충: 시제·역할 표지 목록(O-13, 2026-10-18 임시 구현)

상태: **A 확정(D-38, 2026-10-18)**. 서버 날짜 검증(`agent_runtime/dates.py`, `TENSE_MARKERS_VERSION=tense-ko-provisional-v4`)에 임시 목록을 넣었다. 독립 검증 두 차례(TS-26)를 거쳐 정한 원칙은 다음과 같다.

- 인용(date_quote) 안의 날짜는 정확히 하나다. 사건 역할과 시제는 **날짜 뒤에 붙은 말**에서만 본다(한국어는 서술어가 뒤에 온다). 날짜 앞의 "신청한"이나 다른 문장의 "다녀온"은 이 날짜의 시제가 아니다.
- 사건 기준(date_basis)마다 날짜 뒤에 그 사건의 동사나 명사가 있어야 한다. 시제는 그 사건의 동사에서만 본다. 명사만 있으면("11월 3일 출장") 역할은 맞지만 시제를 모른다(연도가 있거나 오늘·어제 같은 상대 날짜면 그대로 쓴다).
- 날짜 뒤에 다른 사건의 동사만 있으면("어제 신청한 출장", "11월 2일 출장을 신청했") 그 날짜는 이 사건의 날짜가 아니다.
- 연도 표지·범위는 인용이 들어 있는 **문장 전체**에서 본다(모델이 날짜만 잘라 인용해 피하지 못하게).

| 구분 | 임시 목록 |
|---|---|
| 출장 시작일(trip_start) | 동사 출발·떠나·다녀, 명사 출장. 완료 출발한/했·떠난·다녀온, 예정 출발하는/할·떠날·다녀올·출발 예정·출장 예정 |
| 교육 시작일(training_start) | 동사 시작·개강, 명사 교육·과정·연수. 완료 시작한/했, 예정 시작하는/할/한다·시작 예정·교육 예정 |
| 신청·결재·처리·근무일 | 신청·요청·접수·제출 / 결재·승인(결재 받은·받을) / 처리 / 근무·출근 |
| 공통 | "었던·였던"은 완료 표지라 "예정이었던"은 섞임으로 되묻는다. "시작한다"는 예정이다 |
| 연결형 | 날짜 뒤가 "출발해서·시작하고"처럼 시제 없는 연결형이면 같은 문장 뒤쪽의 주 서술어("…돌아온")로 시제를 정한다 |
| 날짜 표현 | `YYYY년 M월 D일`·`YYYY.M.D`·`YYYY-M-D`·`YYYY/M/D`, `작년·올해·내년·재작년·후년 M월 D일`(run 고정 시각으로 연도), `M월 D일`, `M/D`, 오늘·내일·모레·내일모레·어제·그제·그저께(낱말 경계, "그제서야"는 아님) |
| 되묻기 | 날짜 둘 이상, 없는 달력 날짜, 문장 안의 떨어진 연도 표지("2024년 … 11월 5일"), 범위(부터·까지·~), 가정(-다면·-한다는), 시제 없음·섞임, 예정인데 90일 안에 그 날짜가 없음, 이력 메시지의 상대 날짜, 시작일 기준에 끝 역할(돌아온·복귀·귀국·정산·마친·종료·마감) |

목록 밖 표현은 모두 되묻는다(조용히 틀린 연도보다 추가 질문이 낫다는 P-05 B의 안전 쪽). 예: "11월 3일에 출장 가요"("가요"는 목록 밖), "지난 11월 5일"("지난"은 연도 표지가 아님). 추론한 연도는 인용 DTO의 `year_inferred`와 date_evidence에 남는다. 답변 문장의 "2026년으로 보고 답합니다" 표시는 프롬프트 규칙이며 서버가 강제하지 않는다.

| 선택 | 장점 | 비용·제약 |
|---|---|---|
| A. 임시 목록을 확정하고, 평가에서 놓친 표현이 나오면 목록에 더함 | 의존성 없음. 동작을 시험으로 고정할 수 있음(`tests/test_event_dates.py`) | 자연스러운 표현 일부("출장 가요", "참가한 뒤")가 되묻기로 빠진다. 목록 관리가 필요 |
| B. 형태소 분석기(예: kiwi)로 시제 어미와 수식 관계를 판정 | 표현 범위가 넓다. "날짜가 어느 동사에 걸리는가"를 더 정확히 볼 수 있다 | 새 의존성·모델 파일. 분석 오류도 결국 되묻기 규칙이 필요하다 |
| C. 모델이 시제(past/future)를 인자로 내고 서버는 그 표지가 인용에 있는지만 확인 | 서버 코드가 작다 | 표지 확인 규칙이 결국 같은 목록을 요구한다. 판정 근거가 모델 쪽으로 옮겨 감 |

## P-10 live_clock 교육 상태의 계산 시점

상태: **A 확정(D-44, 2026-10-18)**. 2026-10-17 M1 독립 검증에서 나온 질문이다. A를 그대로 쓴다.

MOD-04는 live_clock에서 "cancelled를 우선 보존하고 ends<=clock이면 completed, 그 외 scheduled로 재산출한다"고 정했다. 다시 계산하는 시점이 seed 때인지 조회 때인지는 정하지 않았다. fixed_status(테스트·재현 시나리오)는 어느 쪽이든 영향이 없다.

| 선택 | 장점 | 비용·제약 |
|---|---|---|
| A. seed 때 계산해 저장(현재) | 저장된 status와 조회 결과가 같아 단순. 목록 필터(기본 scheduled)를 DB 조건 그대로 쓸 수 있음 | 시간이 지나면 저장된 상태가 낡음. 데모 중 교육이 끝나도 다시 seed하기 전까지 scheduled로 보임 |
| B. 조회 때 서버 시각으로 계산 | 실제 시간 진행 데모에서 상태가 항상 맞음 | 목록의 scheduled 필터를 계산식으로 바꿔야 하고(cancelled 제외 + ends_at > now), 저장된 status와 화면 상태가 달라질 수 있음 |
| C. A + 데모 시작·주기적 재seed | 구현 변경이 작음 | 재seed를 잊으면 A와 같음. 운영 절차가 늘어남 |

## P-13 "대화 자료"를 넣는 위치

상태: **B 선택**(D-34, 2026-10-17 사용자 확인). 문서 passage는 실제 호출한 도구의 tool_result로만 넣고, 검증된 대화 자료는 현재 사용자 턴 앞의 표시된 자료 블록으로 옮긴다. system에는 규칙만 둔다. 2026-10-17 M2 독립 검증에서 나온 질문이었고 M2 구현은 A였다.

검증된 교육 사본은 지금 system 프롬프트 끝에 JSON 줄로 붙는다. JSON 이스케이프로 줄바꿈을 이용한 블록 탈출은 막혔다(검증 에이전트 실행). 하지만 제목에 지시처럼 쓰인 문장이 있으면, 가장 권한이 높은 위치(system)에 그대로 들어간다. 교육 값은 서버 fixture라 지금 위험은 낮다. 같은 방식이 M3 문서 원문으로 이어지면 T-34(프롬프트 주입)와 직접 관련된다.

| 선택 | 장점 | 비용·제약 |
|---|---|---|
| A. system 끝에 "자료일 뿐 지시가 아니다" 표시와 함께(현재) | 구현 단순, 매 턴 같은 위치 | 자료가 지시와 같은 권한 위치에 놓임 |
| B. 사용자 턴 앞에 별도 "자료" 블록으로 | system과 자료를 분리 | 대화 이력 구성이 복잡해지고 캐시 효율이 떨어질 수 있음 |
| C. 도구 결과 형식(tool_result)으로 재주입 | 모델이 "도구가 돌려준 자료"로 다루는 기존 경로와 같음 | 실제로 호출하지 않은 도구 결과를 만드는 셈이라 기록·감사 해석이 헷갈림 |

## P-15 manifest 검수와 available_from을 정하는 방법

상태: **B 확정(D-36, 2026-10-18)**. 2026-10-17 M3 manifest 초안에서 나온 질문이다. 지금은 100건 모두 needs_review라 개발 DB에 게시하지 않았다. 시험 DB에서만 시험 전용 값(아래 B와 같은 규칙)으로 게시해 기능을 검증했다.

|---|---|---|
| A. 사용자가 manifest를 파일별로 검수해 값을 직접 정함 | 명세에 가장 가깝다. 오류를 사람이 잡는다 | 100건 검수 시간이 든다. 그 전까지 개발 DB 게시·실제 문서 smoke가 막힌다 |
| B. 규칙을 사용자 결정으로 확정: available_from = 각 판본 시행일 00:00 KST(가상 회사가 시행일에 공개했다고 본다). 나머지 제안값은 일괄 승인하고 이상한 것만 고침 | 바로 게시할 수 있다. GA-090(10/6 시행)을 9/29 시점 지식에서 빼는 시나리오가 그대로 동작한다 | 공개 시각을 "추정"이 아니라 "가상 회사 설정"으로 정하는 것이라 문서에 결정으로 남겨야 한다. 시행일보다 먼저 공개된 문서(예고 공지)는 표현할 수 없다 |
| C. available_from = 검수일(예: 2026-10-17 00:00 KST)로 일괄 | 단순하다 | 모든 문서가 같은 날 공개된 것이 되어 과거 지식 시점 조회가 의미를 잃는다(GA-090 시나리오 깨짐) |

추천은 B다. 가상 회사의 설정 값이라 원문에서 "추정"하는 것과 구별해 D 표에 남기면 명세의 취지(근거 없는 값을 사실처럼 쓰지 않음)를 지킬 수 있다.

<a id="p-16"></a>
## P-16 모델이 도구를 부르지 않고 빈 최종 답을 낼 때

상태: **B 확정(D-37, 2026-10-18)**. 2026-10-18 M3 실제 모델 smoke에서 나온 질문이다([TS-24](portfolio/troubleshooting.md#ts-24)). 지금 구현은 A(명세대로 무효 출력 → 실행 실패)이고 프롬프트만 조정했다.

모델(Claude Haiku 5.5, thinking 끔, 최종 답은 JSON 스키마)이 첫 응답에서 도구를 하나도 부르지 않고 `{"answer": "", ...}`(출력 약 45토큰)를 내는 경우가 있다. 서버는 이를 MODEL_OUTPUT_INVALID로 거절한다(T-07의 의도한 방어). 사용자는 502를 받는다. 검색을 한 경우에는 매번 맞는 원문을 인용했다. 문서 질문에서 이 현상은 프롬프트 변형 4개·25회 진단 뒤에도 6개 중 2개(m3-docs-4) 남았다. 명세는 "무효 출력은 failed"([실행 정책](05-agent-execution.md))라 서버가 모델을 다시 부르는 보정은 정책 변경이다.

| 선택 | 장점 | 비용·제약 |
|---|---|---|
| A. 그대로(무효 출력은 실패, 프롬프트만 조정) | 명세 그대로. 추가 호출 없음 | 문서 질문 일부가 502로 끝난다(이번 측정 2/6). 프롬프트 변경마다 측정이 흔들렸다 |
| B. 첫 응답이 "도구 호출 없음 + 빈 answer"이면 서버가 한 번만 다시 부른다. 다시 부를 때 "빈 답은 받을 수 없다, 필요한 도구를 먼저 호출하라"는 서버 문구를 붙인다. 모델 시도 상한(6) 안에서만 | 실패의 대부분을 회복할 가능성(추정, 측정 전). 서버 판단이 단순하고 기록에 남는다 | 05-agent-execution의 재시도 규칙(일시 오류만 1회)을 넓히는 변경. 호출 1회 비용이 더 든다(문서 질문 기준 입력 약 4,900토큰, 약 $0.0005) |
| C. 도구가 있을 때 첫 모델 호출에 tool_choice=any(도구 하나는 반드시 호출) | 도구 없이 끝나는 경로 자체가 없어진다 | 도구가 필요 없는 질문(인사·범위 밖)에도 도구를 부르게 된다. 모델의 도구 선택(T-05)을 서버가 제한한다 |
| D. 최종 답을 JSON 스키마 대신 "답 제출" 도구로 받고 매 호출 tool_choice=any | 응답 형식이 모두 도구 호출로 통일된다 | MOD-07·MOD-02 계약을 크게 바꾼다. 효과는 측정 전이다 |

추천은 B다. 명세의 실패 처리는 유지하되, "아무것도 하지 않은 첫 응답"이라는 좁은 경우만 1회 보정하고 그 사실을 run 기록에 남긴다. 결정 전에는 바꾸지 않는다.

측정(D-37 구현 뒤, 2026-10-18 `m3-docs-9`): 문서 smoke 6개 중 빈 첫 답 2건에서 재호출이 동작했지만 두 건 모두 두 번째도 빈 답이었다(회복 0/2). 더 강한 보정(재호출 때만 tool_choice=any로 도구 호출 강제, 선택 C의 일부)은 이 결정 범위 밖이라 넣지 않았다.

## P-17 사건 날짜의 근원 검증(사용자 메시지 구간 대조)

상태: **B로 구현(명세 이행)**. 2026-10-18 M3 Agent 연결 독립 검증에서 나온 질문이다. 처음에는 결정 사항으로 올렸지만, B는 [사건 날짜 계약](contracts/02-business-dates.md)이 이미 요구하는 동작이라 새 정책이 아니다. 계약대로 구현하고 모델 입력에 date_quote를 더한 것만 계약에 적었다. 구현 전에는 모델이 넣은 `as_of_date`를 그대로 썼다(`date_evidence.source=model_argument`).

[사건 날짜 계약](contracts/02-business-dates.md)은 사건 날짜를 사용자 메시지 구간(CP-07 ReadUserEvidence) 또는 검증된 교육 receipt로 확인하라고 한다. 사용자가 날짜를 말하지 않았는데 모델이 오늘 날짜를 넣으면 지금은 그대로 검색·인용된다(검증 에이전트 실행으로 재현). 프롬프트에 "오늘로 짐작하지 않는다"는 규칙만 있다.

| 선택 | 장점 | 비용·제약 |
|---|---|---|
| A. 지금처럼 모델 인자를 쓰고 date_evidence에 출처를 남김 | 구현 없음 | 명세의 근원 위조 방어(T-15)가 없다 |
| B. 명세대로: 모델이 날짜와 함께 사용자 문장 인용(user_quote)을 내고, MOD-02가 CP-07로 그 구간이 본인 메시지에 있는지·날짜로 정규화되는지 확인. 실패하면 되묻기 | 명세와 일치. 오늘 날짜 위조를 막는다 | search_documents 인자와 MOD-01 ReadUserEvidence 구현이 필요하다. 상대 날짜("지난주 화요일") 정규화 규칙(O-13)이 함께 필요하다 |
| C. 서버가 사용자 메시지에서 날짜 표현을 직접 찾아 모델 인자와 대조 | 모델 출력 형식을 덜 바꾼다 | 날짜 표현 파서를 서버가 가져야 한다. 표현이 여러 개면 어느 사건인지 모델 도움이 필요하다 |

추천은 B다. 결정 전에는 바꾸지 않는다.

## P-18 여러 사건 중 일부만 날짜를 확인하지 못했을 때

상태: **B 확정(D-39, 2026-10-18)**. 2026-10-18 날짜 검증 재검토(TS-26)에서 나온 질문이다. "9월 29일에 시작한 교육과 다음 출장의 한도"처럼 사건이 둘이고 한쪽만 날짜가 확인되면, 지금은 확인된 사건의 인용이 하나라도 있으면 서버가 결론을 바꾸지 않는다(answered). 확인 못 한 사건에 대해 되묻는 일은 모델 답 문장에 맡겨진다. 대표 근거가 예산으로 빠진 경우만 서버가 그 검색 단위로 기권시킨다([05-retrieval-assembly](contracts/05-retrieval-assembly.md) 6항).

| 선택 | 장점 | 비용·제약 |

| A. 지금처럼 모델 답에 맡김 | 구현 없음. 확인된 사건의 답은 그대로 준다 | 모델이 확인 못 한 사건의 금액을 근거 없이 쓰면 서버가 막지 못한다(인용 없는 문장은 원장 대조 대상이 아님) |
| B. 확인된 사건은 답하고, 확인 못 한 사건의 되묻기 문구(서버 문구)를 답 끝에 붙임. outcome은 answered 유지 | 부분 답의 사용성을 지키면서 되묻기가 빠지지 않는다 | 답 문장에 서버 문구가 섞인다. 모델이 이미 같은 질문을 했으면 중복될 수 있다 |
| C. 하나라도 확인 못 하면 전체를 needs_clarification으로 바꿈 | 가장 보수적 | 확인된 사건의 답까지 버린다 |

## P-19 문서 우선관계(authority_relations)와 경과조항 확장(transition_relations)

상태: **B 확정(D-40, 2026-10-18)**. T-17 구현(2026-10-18) 중 확인했다. 명세는 두 관계를 "검수된 값이 있을 때만" 쓰라고 하는데, 지금 manifest는 100건 모두 두 값이 빈 목록이다(초안 생성기는 원문에서 관계를 추정하지 않는다). 그래서 현재 동작은 다음과 같다.

- 안내(FAQ·매뉴얼)는 규정을 바꾸지 못한다(메타데이터 계약에 명시된 우선관계, 프롬프트 규칙).
- 그 밖의 충돌(규정끼리, 공지와 규정)은 우선관계 정보가 없으므로 양쪽 원문을 인용하고 확정하지 않는다(프롬프트 규칙). 서버가 두 원문의 충돌 여부를 판정하지는 않는다.
- 반대편 판본 경과조항(CM-092 제9조, IT-041 제13조)은 회수하지 않는다. 그 사건은 기본 판본만으로 답한다.

정해야 하는 것: (1) authority_relations의 형식(관계 종류: 위임·예외·상위 규정, 대상 document_key, 적용 구간, 근거 조항)과 실제 값, (2) transition_relations의 실제 값(사건 표현을 어느 닫힌 값으로 볼지, O-02), (3) 두 사건이 필요한 경과조항(상신일+승인일)을 위해 search_documents가 사건 날짜 여러 개(verified_events)를 받는 방법.

| 선택 | 장점 | 비용·제약 |
|---|---|---|
| A. 지금처럼 관계 없이 운영(안내 < 규정만 적용, 나머지 충돌은 양쪽 표시, 경과조항 미회수) | 추정한 우선관계를 쓰지 않는다 | 경과조항 대상 사건(개정 직전 상신·직후 승인 등)에 기본 판본만으로 답해 틀릴 수 있다. 평가에서 해당 문항은 실패로 남는다 |
| B. 사용자가 두 관계의 실제 값을 manifest 검수 때 채우고(P-15와 같은 검수), 개발자는 형식·검사·회수(ExpandTransitionEvidence)와 복수 사건 입력을 구현 | 명세대로. 경과조항 사례를 정확히 답한다 | 검수 작업이 필요하다. search_documents 인자 확장(사건 날짜 여러 개)과 날짜 검증(TS-26 규칙)을 사건마다 적용해야 한다 |
| C. 경과조항이 있는 문서의 개정 경계 근처 사건은 서버가 항상 되묻거나 기권 | 틀린 답을 막는다. 관계 값 없이 가능 | "경계 근처"의 범위를 정해야 하고 답할 수 있는 질문도 막는다 |

추천은 B다(검수 전까지는 A로 둔다). 결정 전에는 바꾸지 않는다.

구현(D-40, 2026-10-18): 관계 형식·검사·회수와 other_events를 구현했고, 값은 `review-manifest`가 원문으로 만들었다(우선관계 48건은 본문 명시 문장, 경과조항은 CM-092 제9조·IT-041 제13조 2건). 다른 경과 문구("제2조(적용관계)" 보관본 문구, ED-031 제8조, ED-021 제20조)는 사건 조건이 기본 판본 선택과 같거나 일반 원칙이라 넣지 않았다.

## P-21 M4 Wiki 주제·분할·검수(O-06·O-08)

상태: **A 확정(D-45·D-46·D-48, 2026-10-18, D-41 진행 규칙으로 추천안 채택)**. 명세가 "주제 분할·검수 항목·권한별 분할 필요"를 M4 빌드 전 검토로 남긴 값들이다.

| 항목 | A(채택) | 다른 선택지와 trade-off |
|---|---|---|
| 주제를 정하는 방법 | 모델이 도메인별로 문서 제목·종류만 보고 초안을 쓰고, 빠진 문서는 단독 주제로 채운 뒤 검수 표시(review-wiki-topics) | B: 문서 하나 = page 하나 → 다문서 종합 질문(40문항)에 Wiki가 줄 수 있는 연결이 사라진다. C: 도메인 하나 = 주제 하나 → 주제당 15~25개 문서라 page 입력이 커지고 요약이 흐려진다. D: 본문까지 보고 주제 생성 → 비용이 크고, 주제 정의에 평가 문항과 겹치는 내용이 들어갈 위험이 커진다 |
| page 분할 | 주제 × 권한 등급 × (규범 시행 구간 \| 안내 유효 기간). 안내는 규범 구간 page와 분리 | B: 주제당 page 하나 + 권한 교집합 → 제한 문서 하나가 섞이면 그 주제 전체가 공개 사용자에게서 사라진다. C: 안내를 모든 구간 page에 넣기 → 현행 FAQ 문장이 종전 구간 요약에 섞인다(이번 시험 corpus에서 확인) |
| 자동 검사 | 주장마다 링크 1개 이상, 라벨이 page 입력 passage, 인용이 원문의 연속 구간(공백 정규화), 4~300자. 실패 시 문제를 알려 1회 재생성 후 미게시 | B: 실패 즉시 build 전체 실패 → page 하나 때문에 전체를 다시 만들어야 한다. C: 틀린 주장만 지우고 게시 → 원문 링크가 해석되지 않은 page는 게시 실패 또는 명시된 미게시 항목이어야 한다는 CT-15와 어긋난다 |
| 의미 검수 | 독립 검수 에이전트(모델)가 page마다 approved/rejected, reviewer_kind=model로 기록하고 보고서에 밝힘 | B: 사람이 전부 검수 → 이 프로젝트에는 검수자가 없다. C: 검수 생략 → 링크 존재 검사는 의미 충실성을 보장하지 않는다(MOD-10) |
| 탐색 설정 | 질의 벡터 공유, page 5개 → 링크 전체 펼침 → raw와 같은 필터·원문 거리 정렬 20개 | B: Wiki 거리 순서를 원문 순서로 쓰기 → A/B의 정렬 기준이 달라 Wiki 효과와 정렬 효과가 섞인다. C: page 본문을 근거로 넘기기 → 최종 근거가 원문이 아니게 된다(금지) |

## P-22 비교 실행 설정(O-07)

상태: **A 확정(D-49, 2026-10-18, D-41 진행 규칙으로 추천안 채택)**.

| 항목 | A(채택) | 다른 선택지와 trade-off |
|---|---|---|
| 예산 후보 | 4000·8000·12000 | B: 4000·6000·8000 → 촘촘하지만 큰 문맥에서 hard negative가 늘어나는 지점을 못 볼 수 있다. C: 4000·16000·32000 → 비용이 크고 이 corpus(passage 대부분 수백 token)에서 20개 후보를 다 넣어도 넘기 어려운 값이라 정보가 적다 |
| 패킹 순서 | 현재 구현 `group-relevance-v1`(대표 거리 순, 그룹 연속, 끊지 않음) | B: 관련도 높은 그룹을 앞뒤 양끝에 배치 → 긴 문맥 중간 손실을 줄일 수 있지만 새 구현·새 변인이다. dev 진단만 하고 바꾸지 않는다(docs/13) |
| 반복·seed | dev 1회, judge 순서 seed 20261018 | B: 3회 반복 → 분산을 잴 수 있지만 비용 3배·Gemini 무료 티어 한도 초과 |
| 동결 규칙 | 규칙 정답률이 더 오르지 않거나 hard negative 인용 오답이 늘기 시작하는 가장 작은 예산, 동률이면 작은 값 | B: 정답률 최대 예산 → 작은 차이로 큰 예산을 고르게 되고 holdout 비용이 커진다 |

## P-23 규칙 정답 정의(평가 채점)

상태: **A 확정(D-51, 2026-10-18, D-41 진행 규칙으로 추천안 채택)**.

| 항목 | A(채택) | 다른 선택지와 trade-off |
|---|---|---|
| answered 정답 | 근거 하나 이상 인용 + 두 자리 이상 숫자 사실 모두 + 금지 숫자·별도 그룹 HN·누출 없음. 근거 집합 전체 인용은 rule_complete로 따로 | B: 인용 하나만 맞으면 정답(처음 구현) → 금지 금액을 말해도 정답이 돼 예산 동결 기준이 부풀려진다(독립 검증 재현). C: 모든 숫자(한 자리 포함)를 요구 → "1회 과정"처럼 사실의 핵심이 아닌 숫자 때문에 맞는 답이 오답이 된다(시험에서 확인). D: 근거 집합 전체 인용을 요구 → 답에 필요한 핵심만 인용한 정답을 깎는다 |
| 같은 그룹 HN | 인용하고 틀린 경우만(금지 숫자와 함께) | B: 인용하면 오답 → 정답 조항과 같은 표에 있어 정답 회수 때마다 걸린다(docs/13) |
| 누출 범위 | 인용·문맥·패킹 전 후보 파일 + 답 속 제한 문서 제목, 판정 불가 문서는 unscorable | B: 인용·문맥만 → 후보 단계 누출과 제목 누출을 놓친다 |
